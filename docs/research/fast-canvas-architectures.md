# How fast 2D canvas/diagram apps stay smooth: findings for Qraw

Date: 2026-11-26. Written before the canvas work was done; the implementation is described in ARCHITECTURE.md and DECISIONS.md (D-030 to D-037) and the findings are kept as background. Scope: advise the canvas-performance design (decode-once image cache + mips, exact invalidation, tiled backing store per zoom bucket, off-thread tile raster on an immutable snapshot, snapshot-bitmap dragging, LOD, CPU compositor behind an interface).
Constraint: Qt 6 Widgets / C++20, no new libs, no GPU API now.

Legend: [P] primary source (vendor docs/source/design doc), [S] secondary (third-party summary, notes, blog about it), [U] unverified / from memory. Fit = High/Med/Low for Qraw.

## 0. What the codebase already had (at the time of writing)

Observations about the codebase when this was written:
- `render::Canvas` (src/render/include/qraw/render/canvas.h) is a call-for-call port of mxAbstractCanvas2D: ~35 virtual state/path/paint ops plus `image(ImageData)`, `text(TextBlock)`, `beginGroup/endGroup(cellId)`. Backends: PainterCanvas, SvgCanvas, SketchCanvas, and a test RecordingCanvas. So a **display-list recorder already exists in spirit**; every shape/label/marker painter targets this interface. That is exactly the "record once, replay many" seam Chrome (PaintRecord), Skia (SkPicture), Android (RenderNode) and Flutter (DisplayList) all use.
- `ImageData` holds a `QByteArray` (implicitly shared), so a recorded op can reference image bytes without copying; this also supports sharing multi-MB style strings.
- The scene build took 744 ms at 50k cells and `move` 208 ms, i.e. the QGraphicsItem-per-cell overhead was itself significant beyond painting.

## 2. What is publicly known vs unknown about Apple (Freeform / PencilKit)

- Known [S]: Core Animation commits a layer tree to an out-of-process render server that draws each frame; committed animations run there without app involvement (WWDC14-419 notes). `shouldRasterize` composites a layer to a bitmap once; Apple/WWDC advice is "only for static content" because content updates add offscreen passes. visionOS docs say shadows/masks/blurs/rounded rects raise offscreen-pass counts.
- Known [S, weak]: a WWDC 2026 session text says PaperKit builds on PencilKit and Freeform on macOS "is also PaperKit". A third-party "infinite" PencilKit canvas is just a 1,000,000 x 1,000,000 pt canvas.
- Apple's own guidance for drawing apps [S via search]: switch to Metal when needed; avoid transparent Metal layers and blur overlays for latency.
- **Unknown: how Freeform renders** (tiles, CATiledLayer, Metal, caching, threading). No public source. "Freeform-inspired" in the plan is therefore inspiration by analogy to Core Animation concepts (retained layers, off-process composition, property-only animation), not a documented design to copy. CATiledLayer's documented model (tiles drawn on background threads, levelsOfDetail, tiles blank then fade in) [U, from memory] is the closest public Apple analogue to the plan's tile design, and note it leaves tiles blank while pending, which Chrome/MapLibre avoid (section 3.4).

## 3. Techniques

### 3.1 Record once per cell into an immutable display list; replay into tiles (the central missing piece)
- What: run shape/label logic once into an op buffer (path ops, state, image refs, text blocks); raster = replay ops clipped to a tile. Recording is zoom-independent (model units); replay applies the tile transform.
- Who: Chrome (`PaintRecord`/`PaintOpBuffer` = SkPicture equivalent; "recording is cheap compared to raster", JPEG/PNG kept encoded during record [P impl-side doc]); Skia SkPicture (replayable, `approximateOpCount`/`approximateBytesUsed`, cull rect; R-tree bounds per op) [P]; Android RenderNode (display list + separate properties; child referenced by DrawRenderNode, not copied; parent not re-recorded when child changes) [P/S]; Flutter DisplayList [P].
- Evidence: Chrome's raster-thread design rests on it; Skia RTree gave a small raster win in Chrome perf tests and "much larger" with later painting changes; 5-7% on .skps in one review [P, old]. No public absolute numbers for Qraw-like workloads. There is **no evidence** that record cost is small relative to raster for draw.io stencils; that must be measured (see 4.1).
- Fit: **High**. The plan's "immutable render snapshot" is much cheaper and safer if the snapshot is `vector<shared_ptr<const CellRecord>>` in z-order (copy-on-write per edited cell) instead of a deep copy of cells+styles (which would copy multi-megabyte base64 style strings). Workers never touch the Document, styles, or shape registry; thread-safety then becomes "immutable data + QImage per tile".
- Qt mapping: add `RecordingCanvas : Canvas` (the test one is a seed) producing `std::vector<Op>` (tagged union or variant; paths as `QPainterPath`/`geometry::Path` shared_ptr, `ImageData` by value (implicitly shared bytes), text as resolved TextBlock). `replay(PainterCanvas&)` in worker threads. Do NOT use QPicture: its docs say nothing on thread-safety beyond "usable as a paint device in a non-GUI thread, one thread per device", nothing on text-as-text vs glyphs, it uses an opaque serialized stream format (re-parsed on replay), and it cannot carry your gradient/shadow/dash semantic ops; own op buffer is also what a later QRhi backend would consume.
- Caveats: (a) text. Replay of `text(TextBlock)` still lays out a QTextDocument per label unless the record stores laid-out glyph runs (3.9). (b) Ops needing the current transform scale (stroke widths, dash multiples, shadow offsets "scaled by current scale") are fine because replay passes the tile transform through the same Canvas semantics. (c) record per-op bounds only if cell-level culling is insufficient; a cell record bbox is enough for tile membership, and a cell spanning tiles gets replayed per tile (duplicated work; Chrome relies on R-tree culling inside the picture; large swimlane containers with many children are the Qraw worst case, so record container shape and children separately: Android's DrawRenderNode reference pattern).

### 3.2 Separate content from properties (transform/alpha) so moves don't re-record
- Who: Android RenderNode properties vs display list; Core Animation layer properties; Chrome property trees (transform/clip/effect trees; "O(interesting nodes) instead of O(layers)") [P].
- Fit: **High**. A drag changes only translation. With 3.1, a dragged cell's record is reused; only its position changes. This subsumes "snapshot-bitmap dragging" in the plan: dragged cells can be drawn **live from their display lists** every frame (vector-sharp at any zoom, no bitmap resampling), while the static tiles stay untouched. Bitmap dragging is still the right fallback when a drag set is huge (>~N ops or tens of cells): choose by `approximateOpCount`-style cost.
- Qt mapping: CellRecord = {content (immutable shared), bounds}, placement = {x,y,rotation, alpha} separate. Edges attached to moved vertices must re-record (path changes), so edges are "content changes"; keep them in the live layer during drag too.

### 3.3 Layer split: static tiles / active layer / overlay (Excalidraw, Chrome layers)
- Who: Excalidraw has a static-scene canvas ("the non-ui canvas where we render elements") and a separate interactive canvas (selection, handles) [P/S: staticScene.ts docstring; interactive config type seen in a published .d.ts]. Chrome promotes independently-changing content into separate layers; Flutter `RepaintBoundary` exists to contain repaints "critical to minimizing redundant work" [P]. tldraw never culls selected/edited shapes [P].
- Fit: **High**, and missing as an explicit item. Plan's "exact invalidation" removes FullViewportUpdate but selection chrome, hover, rubber band, connection handles, guides, and live-dragged/edited cells must never invalidate tiles.
- Qt mapping: (1) tile layer drawn in `QGraphicsView::drawBackground` or the viewport paintEvent; (2) active layer = cells being dragged/resized/text-edited, replayed live; static tiles must not contain them, so at drag start mark the affected tiles "re-raster excluding set S" once (async; keep old tile visible, 3.4) or simply let the active layer paint over (cheap trick: opaque cells hide the old copy; **wrong** for transparent/shadowed cells, so use exclusion); (3) overlay = existing handle/selection items. Set `QGraphicsItem::ItemHasNoContents` on CellItems whose pixels come from tiles (flag exists in Qt, skips paint; verify it also skips the per-item painter save/restore) and keep CellItems only for hit-testing/selection geometry.
- Also consider `QGraphicsView::DontSavePainterState` for the overlay items once they restore their own state [P: Qt docs].

### 3.4 Never show blank: stale-while-revalidate, other-scale fallback, gesture-time scaling
- Who: Chrome keeps old-scale tilings as fallbacks, snaps new raster scale to an existing tiling when within ratio 1.2, allows ~2x drift during pinch, and rasterizes the ideal scale after the gesture [P constants; S analysis]. Checkerboard is the last resort; the design aims to fill gaps "without starting a new commit" [P]. MapLibre keeps tiles "as substitutes for pending loading tiles" and draws an overscaled parent [P/snippet]. Excalidraw during zoom gestures leaves "bitmaps at the old scale and resampled" [P comment]. tldraw `getEfficientZoomLevel` holds a stable zoom during camera motion when >500 shapes (debounced) [P].
- Fit: **High**. The plan names zoom buckets but not the fill policy.
- Qt mapping, in draw order for a missing tile: exact bucket tile -> same area from nearest other bucket (up- or down-scaled with `drawImage` with `SmoothPixmapTransform` only when scale <1; nearest/bilinear when large upscales for speed) -> page background colour. Tile cache key = (bucket, tx, ty); fallback lookup walks neighbouring buckets. Add hysteresis on bucket switch (e.g. switch up at 1.2x past the boundary like Chrome's snap ratio) and defer re-raster until zoom settles for N ms (tldraw debounce). Edits: keep the old tile displayed until the new version lands (stale-while-revalidate), see 3.6 for the small-edit exception.

### 3.5 Raster-cache admission heuristics (Flutter)
- What: Flutter's RasterCache caches a subtree only after it has been prepared/drawn `access_threshold` = 3 frames; entries limited per frame (`picture_and_display_list_cache_limit_per_frame`, "may cause jank on that frame... distribute the work across multiple frames"); entries not encountered this frame are evicted at the start of paint; memory estimate counts only SkImage bytes [P raster_cache.h]. Default of 3 and the per-frame cap are the facts; the exact current default constant value for the cap was not in the file.
- Fit: **Med** for per-cell bitmaps (with tiles you mostly don't need per-cell bitmaps); **High** for the idea applied to tiles and to expensive cells: admit a cell/tile to a cache only if unchanged for N frames; cap new rasters per frame; evict anything not touched this frame beyond budget. During drag/typing, content changes every frame so nothing gets cached, which is the right behaviour and avoids "raster then immediately invalidate" thrash.
- Qt mapping: `QGraphicsItem::DeviceCoordinateCache` is the stock per-item bitmap cache but is item-level, regenerates on any scale change, and its memory is unmanaged [P docs: "suits items that move but aren't rotated, scaled, or sheared"]; do not rely on it. Own cache: `struct TileEntry{QImage img; version; lastUsedFrame; unchangedFrames;}`.
- Cheap per-cell cache worth keeping: only for **expensive** cells (many ops, big images, blur/shadow), selected by a cost estimate on the record (Skia exposes `approximateOpCount`). Flutter's own guidance: avoid `saveLayer`/opacity groups, precompute static overlapped translucent results [P perf doc]; Qraw analogue: group alpha/shadow cells are the expensive ones.

### 3.6 Scheduling: priority bins, few in-flight tasks, cancel-by-generation, small tasks, sync fast path
- Who: Chrome TileManager sorts tiles into bins "needed now / needed within the next second / needed eventually / never" then by distance, assigns memory budget in that order; tasks "cannot be cancelled once started", so it re-submits whole graphs omitting unstarted work and keeps only a limited number enqueued per thread "so reprioritization doesn't cause redundant work" [P]. Raster tasks wait on image-decode tasks as dependencies [P]. If the main thread misses the deadline the scheduler draws without a commit and goes to a "high-latency mode" with more pipelining [P]. Krita: stroke jobs are CONCURRENT / SEQUENTIAL / BARRIER / EXCLUSIVE; canceling a stroke drops its unstarted jobs and runs a cancel job; update-vs-stroke balance by a simple queue-length ratio; "signals from stroke threads can deadlock with Qt::BlockingQueuedConnection" [P].
- Fit: **High**.
- Qt mapping without libs: do not just `QThreadPool::start()` one runnable per tile (can't reprioritize, can't cancel). Use a small custom priority queue on the GUI thread that feeds N=hardware_concurrency-1 workers with at most ~1-2 queued tasks per worker (the Chrome rule). Priority bins: (0) visible tiles of current bucket, (1) tiles intersecting viewport expanded ~1 screen in the pan-velocity direction, (2) next/previous zoom bucket for visible area (for pinch fallback), (3) idle prefetch. Each task carries (snapshot version, generation); worker checks `generation` between cells (cooperative cancel) and the result is dropped on arrival if stale. Results return via `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` only; **never BlockingQueuedConnection** (Krita lesson).
- Tile size: Chrome software raster uses ~256x256 [P how_cc_works]; for Qraw start at 256-512 device px and measure: smaller tiles reduce latency/wasted raster, larger reduce replay duplication of cells that straddle borders.
- Small-edit fast path ([U] as a design inference, not a quote): Chrome rasters on demand for a checkerboarded tile without a commit; analogously, if damage is small and the estimated replay cost (sum of op counts of cells in the tile) is under ~1-2 ms, rasterize that tile synchronously on the GUI thread so typing/small moves never see a thread-hop latency or a stale frame. Everything bigger goes async.
- Atomicity: Chrome stages raster on a pending tree and activates the whole thing so users never see a half-updated page [P]. Qraw equivalent: tiles are versioned by snapshot; for a multi-tile edit, show new versions only once all visible dirty tiles for that version are ready, unless the wait exceeds a budget (~1 frame), then show partial (tearing is usually tolerable for a diagram; blank is not).

### 3.7 Frame scheduling and dirty coalescing
- Who: Chrome cc::Scheduler with BeginFrame deadlines; `DamageTracker` computes screen damage with two kinds: invalidation damage and **expose damage** (layer added/removed/reordered with no raster invalidation) [P]. Krita's processing applicator emits `setDirty()` "in efficient way, so no nodes are updated twice" [P]. Excalidraw static-scene render is throttled to animation framerate, one throttle per canvas [P].
- Fit: **Med-High**.
- Qt mapping: accumulate `QRegion` of dirty rects (both old and new bounds of every changed cell, in tile space too) between frames; a single `viewport()->update(region)` per frame via a ~16 ms single-shot timer or `QWindow::requestUpdate()` on the top-level window [U: that call exists in Qt 5.5+, but whether Widgets repaints align with it is not confirmed here]. Widgets already coalesces multiple `update()` calls into one paint event [U: from Qt knowledge]. Z-order change (raise/lower/reorder) is an "expose damage" case: needs invalidating the union of both cells' bounds even though no cell content changed; easy to forget.
- **Correctness note (high value)**: dirty bounds must be the *visual* bounds including stroke width/2, shadow offset (draw.io shadow = (2,3)*scale), arrowheads/markers, label overflow beyond the shape, rotation, sketch/rough jitter. tldraw documents the failure mode (glow/shadow shapes "pop in and out at the viewport edge" when culled by geometry bounds) [P]. Qt's default 2 px AA expansion in QGraphicsView is also relevant: `DontAdjustForAntialiasing` trades that for "painting traces when items move" [P docs], so don't set it unless bounds already include AA.
- Qt view flags: `FullViewportUpdate` is documented as best "when deciding what to draw costs more than drawing" and preferred for QOpenGLWidget viewports; `MinimalViewportUpdate` is default but costs when many small changes [P]. For a tile compositor you want `NoViewportUpdate` or `BoundingRectViewportUpdate` and your own region management [P: "NoViewportUpdate... suits scenes needing a fixed frame rate or updated externally"]. [U] QGraphicsView implements panning in non-Full modes by `viewport()->scroll()` (blit) and only exposes the strips; so moving off FullViewportUpdate should also give cheap panning, verify in Qt source before relying on it.

### 3.8 Level of detail and zoom bucketing
- Who: tldraw: images served at `steppedScreenScale` (on-screen/native ratio rounded **up to a power of two**), debounced; stickies drop shadows, dashed -> solid, hatch -> solid below thresholds; text outlines off below textShadowLod 0.35; recommends simplifying shapes under ~50 px on screen [P]. Krita LoD strokes ("Instant Preview"): work at reduced resolution first, refine after [P]. CATiledLayer levelsOfDetail [U]. Chrome low-res tiling existed (grida analysis claims removed; unverified) [S].
- Fit: **High**, and plan already has LOD; add: (a) pow-2 stepped buckets + hysteresis (3.4); (b) per-shape *semantic* LOD in the recorder: record two variants lazily (full / simplified: no shadow, no dashes, no gradients, no text below ~4 px font) keyed by bucket; (c) cull sub-pixel cells to a 1 px fill; (d) a cheap "preview" tile pass (e.g. skip images/text, draw 1/4 scale) that can fill in synchronously during fast pan/zoom before full quality arrives.
- Images: decode-once with mips matches Chrome (decode cache with separate decode tasks that raster waits on; `GpuImageDecodeCache`/`SoftwareImageDecodeCache`) [P]. Qraw specifics: Qt's bilinear downscale of a 1000x600 PNG to ~60 px aliases heavily without mips [U: general knowledge], so box-filtered pow-2 mips are the right call; produce mips on a worker as a dependency of the first tile that needs them; key by content hash; budget in bytes (LRU). `QImageReader::setScaledSize` can cut decode cost only for formats whose handler supports it (docs: "depends on the image format"); the docs do not confirm JPEG DCT-scaling, so assume PNG always needs a full decode [P/U].

### 3.9 Text is probably the hidden per-cell cost
- Before the text caches: a fresh QTextDocument layout per label per paint. Everything above fixes *repeat* but not the first cost.
- Facts [P]: QStaticText caches layout data but **re-lays-out when the painter's matrix changes beyond translation** (except OpenGL2) or the font differs; `prepare()` can precompute; AggressiveCaching costs more memory. QPainter can paint onto QImage/QPicture in threads; "QTextDocument created in the GUI thread... use clone()" when pixmap resources are involved. The Qt thread-support page says nothing about QFont/QTextLayout/QFontMetrics thread safety [U: Qt does allow them in worker threads on most platforms if QGuiApplication exists and fonts are initialised from the GUI thread; verify with a TSan run].
- Idea (used by Figma which built its own text layout engine [P 2015 post] and by Chrome via shaped text blobs [U]): lay out text **once in model units, zoom-invariant** (set `QFont::PreferNoHinting` / disable hinting so advances don't snap per scale; wrap width in model units) and store the result in the record as glyph runs (`QTextLayout::glyphRuns()`/`QGlyphRun`, painted with `QPainter::drawGlyphRun`). Benefits: no re-layout per tile or per zoom bucket, no label reflow differences across zoom, threads replay glyph runs not documents. Risk: draw.io HTML labels (`html=1`, `<b>`, `<br>`) need the rich-text path; keep QTextDocument for those but cache its layout per (cell, text-version), and clone for workers. Fit: **High** for layout caching + LOD (skip text below ~4 px, draw a grey line box below ~7 px); **Med** for glyph-run recording (depends on thread-safety verification).

### 3.10 Memory budgets
- Chrome: budget assigned to tiles in priority order [P]; Flutter: bytes = image memory only, no hard cap in the header [P]; Inkscape: default render cache 64 MB, "default tiles 16" [P wiki], devs called the cache "more of a band-aid than an actual solution" and report tearing while panning with cache on and cost when scaling the cache on zoom [S: devel-list thread]; Excalidraw: per-element canvas capped at 32767 px and 16,777,216 px area, "ballpark limits... chosen lower to be safe" [P].
- Fit: **High** (simple). Suggested budget model: tile bytes = w*h*4 * dpr^2 (a 256x256 tile at dpr 2 is 1 MB with 512-px device tiles; Qt's own note that opaque RGB32 / premultiplied ARGB32 are the fast formats is [U]); budget = N viewports of the current bucket + 1 viewport of the fallback bucket, LRU by bin, hard cap in MB configurable. Separate budget for decoded images (+ mips ~1.33x), because 32 PNGs of 1000x600 are ~77 MB decoded at full size. Use opaque tiles (page background baked in) so blits are copies, not blends.

### 3.11 Decouple rendering from QGraphicsScene overhead
- Who: tldraw, Figma, Excalidraw, Atlassian all render from their own model with their own spatial structure; Atlassian chose a sparse **2048x2048 tile map** over quadtrees/k-d trees "because frequent element movement makes tree rebuilding expensive" (8M add / 5M query ops/s) [P]. Qt: BSP index reorganises on item moves; benchmark here: scene build 744 ms @ 50k, move 208 ms.
- Fit: **Med**. Short term: keep QGraphicsScene for hit testing and selection but set `setItemIndexMethod(NoIndex)` only if profiling says BSP maintenance dominates [U], and render nothing through it (3.3). Medium term: your own uniform grid (cell -> tile buckets) is needed anyway for "which cells intersect this tile" in workers (they can't query the scene), so build it into the snapshot.
- Large-scale thinking: visibility culling in all tools is cell-level (tldraw display:none via spatial index; "10,000 shapes, ~50 render") [P].

### 3.12 GPU-ready compositor interface (for the later Vulkan/QRhi step)
- Figma lessons [P 2025/26 post]: make draw calls take their resources as explicit arguments (they fixed stale-binding bugs and enabled WebGPU migration); batch uniform data into one buffer per submit; cache/reuse bind groups; batch draws into fewer passes; keep one shader source; run a dynamic fallback with device blocklists since a mid-session fallback is a visible hitch. No public tiling numbers.
- Fit: **Med** now. Interface sketch: `Compositor::submit(span<const TileRef>, Transform, span<const LayerRef>)`; `TileRef{id, bucket, version, QImage const*, destRect, srcRect}`. Tiles are immutable once published so a GPU backend can upload-once-by-version. Keep premultiplied opaque pixel format and tile sizes power-of-two friendly. Do not expose QPainter in the interface.

## 4. Measurement methodology

### 4.1 Before building: a one-day profile spike (cheap, decides the whole plan)
Split the time of one full repaint of an image-heavy synthetic document and a 10k generated doc into: (a) shape/stencil logic (path construction), (b) QPainter rasterization of those paths, (c) text layout, (d) image decode + scale, (e) QGraphicsView/Item overhead (paint dispatch, state save/restore, index). Use `perf`/VTune-free tools: `perf record` + flamegraph on Linux, `QElapsedTimer` accumulators around Canvas backends (a `TimingCanvas` decorator that forwards to PainterCanvas and bins by op type is trivial given the interface). If (a)+(c)+(d) dominate, record/replay + glyph runs + decode cache are the big wins; if (b) dominates, tiles/culling/LOD are. Chrome's pipeline assumes raster >> record; **do not assume that for Qraw until this is measured**.

### 4.2 Metrics (what to report)
- Chrome: **percent dropped frames** as average, worst 1-second sliding window, and 95th percentile over 1-second windows; do not poll rAF to measure FPS [P web.dev]. Jank flagged when a frame's gap is >1 vsync [P scroll_jank_v4]. Normalise as ratios not per-minute counts so runs at different refresh rates compare [P Chromium commit via search].
- tldraw emits 'interaction-end' events with fps and **p95 frame time** per interaction [P]. Atlassian reports per-phase ms (update 1-2 ms, render 0.4-0.5 ms) and p90 interaction times (drag 2.5 ms, pan 2 ms) on a fixed 5K-element board; benchmark table of p50/p90/p99 over a 50K-element zoom-out+pan script [P]. MURAL: percentage of frames >= 30 fps (no baselines published) [P].
- Inkscape: per-idle-process log (loops, splits, duration, total) and warns run-to-run variance ~0.1 s on the same op, plus dependence on window size, HiDPI, other processes [P] => use medians and many repetitions.
- For Qraw: for each scripted interaction (first paint, pan, wheel zoom, pinch, hover, select, drag 1 / 100 cells, edit label) record per-frame (input->paint-complete) times and report p50/p95/p99 plus "frames over budget" (budget = 1/refresh, e.g. 16.7 ms and 8.3 ms). Extend `qraw-bench --paint FILE --page N` accordingly.
- Separate **latency to settled quality** (time until all visible tiles are exact-bucket and current-version) from frame time; the plan trades one for the other.

### 4.3 CI gating that doesn't flake
Wall-clock budgets on shared CI runners (the repo's CI covers Linux/macOS/Windows; offscreen platform has no vsync) are noisy. Gate on **deterministic work counters** per scripted interaction: cells painted, ops replayed, tiles rastered, bytes decoded, bytes uploaded/composited, cache hit rate, number of tiles invalidated per hover/selection (must be 0). These are exact and catch the regressions that matter (FullViewport-style over-invalidation, re-decode). Keep timing percentiles as advisory/trend (Figma/Atlassian: fixed datasets, headless Playwright+Chromium tracing, dev vs main comparison [P Atlassian]).

### 4.4 Tracing
Emit Chrome Trace Event JSON (a text format; `{"ph":"X","name":..,"ts":..,"dur":..,"tid":..}`) from a tiny in-house scoped timer macro behind a runtime flag and open it in the Perfetto UI or chrome://tracing (external viewers, not linked dependencies). Chrome itself diagnoses smoothness through trace events (`PipelineReporter`, `EventLatency`) [P web.dev]. Track names: input, snapshot, schedule, raster(tile), upload, composite, paint.

## 5. Lessons from things that went badly
- Inkscape: main-thread tile rendering in "idle processes" (can pause to service events) still hitches; rendering cache called a band-aid; cache scaling on zoom was expensive and unfinished; tearing on pan with cache [S]. Lesson: tile raster must be off-thread and the cache must not need main-thread rescaling.
- Krita: scalability bottleneck was lock contention in the tile data manager (extent-manager mutex), fixed by lock-free hash tables and restructuring [P GSoC 2018 report via search]. Lesson: workers shouldn't share a mutable cache; GUI thread owns the map, workers produce independent QImages.
- tldraw: culling by geometry bounds caused popping for glows/shadows; separate "culled" vs "not visible" concepts so selection UI still works [P]. Lesson: bounds must be visual bounds; never cull selected/edited items.
- Excalidraw per-element canvas cache is keyed by zoom, theme, device scale; position/opacity are *not* in the key because they are applied at blit time [P]. Lesson: keep cache keys minimal; apply translation/alpha at composite.
- Atlassian: shader compile at startup cost ~3 s until lazily compiled/pre-warmed on idle [P]. Lesson for Qraw: warm font database, stencil registry, and image-mip generation in idle time after first paint.
- Figma: error checking too often in WebGL hurt perf; readback test added hundreds of ms to load [P]. Lesson: probe/self-test costs at startup matter.

## 6. Ranked recommended changes to the plan

1. **Make a RecordingCanvas display list per cell the render IR** (3.1). Snapshot = vector of shared_ptr<const CellRecord> in z-order; workers replay; no Document/style access off-thread. First do the 4.1 spike to confirm record cost is significant. Fit High.
2. **Explicit layer split** static tiles / active live layer / overlay; hover, selection, handles, guides never invalidate tiles; drag draws moved cells live from their records (replaces bitmap dragging except for huge drag sets) (3.2, 3.3). `ItemHasNoContents` on CellItems; stop painting through the scene. High.
3. **Never-blank fill policy**: stale-while-revalidate, nearest-other-bucket fallback scaled, bucket hysteresis (switch ~1.2x past boundary), zoom-settle debounce, re-raster after gesture (3.4). High.
4. **Correct visual dirty bounds and per-tile versioning**: bounds include stroke/shadow/markers/label overflow; old+new bounds; expose-damage for z-order changes; one coalesced update per frame (3.7). High (correctness bugs otherwise).
5. **Priority-binned scheduler with 1-2 queued tasks per worker, generation cancel, small tile tasks, queued-only results, sync fast path for tiny dirty regions** (3.6). High.
6. **Zoom-invariant, cached text layout** (no hinting, model-unit wrap, cache per cell+text version; optionally record glyph runs), plus text/shape LOD below size thresholds (3.8, 3.9). High for caching, Med for glyph runs (verify thread safety).
7. **Cache admission and budgets** à la Flutter: tiles admitted only when stable N frames (so drag/typing never thrashes), per-frame raster cap, evict untouched, byte budgets for tiles and decoded images; per-cell bitmaps only for measured-expensive cells (3.5, 3.10). Med-High.
8. **Measurement**: spike profile first; deterministic work counters in CI; frame-time percentiles by 1-s windows (avg/worst/p95) for pan/zoom/drag; trace-event JSON + Perfetto UI; separate "time to settled quality" metric (section 4). High.
9. **Image pipeline details**: decode + mip build as a worker dependency of the tile task that needs it; box-filtered pow-2 mips (not Qt bilinear from full-res); content-hash key; encoded bytes shared (implicit sharing of QByteArray in ImageData, no style string copies); bytes-budgeted LRU (3.8). Med-High.
10. **Own spatial grid for tile membership/culling** in the snapshot, since workers can't query QGraphicsScene; evaluate NoIndex for the scene (3.11). Med.
11. **Predictive prefetch**: ring around viewport biased by pan velocity; neighbouring zoom bucket at idle; warm fonts/stencils/mips on idle (3.6, section 5). Med.
12. **Keep Compositor GPU-ready**: immutable versioned tiles, explicit-argument submit, no QPainter in the interface (3.12). Med, cheap now.

## 7. Open questions / unverified items to test rather than trust
- Whether record cost << raster cost for Qraw workloads (4.1). Unknown; no source can answer it.
- Qt thread-safety of QFont/QTextLayout/QGlyphRun/QFontEngine in workers (not in Qt's thread-support page). Test under TSan on Linux, plus Windows/macOS since CI covers all three.
- QGraphicsView `scroll()` blit on pan outside FullViewportUpdate; `ItemHasNoContents` skipping painter state work; `QWindow::requestUpdate` pacing for Widgets. All from memory of Qt source.
- Chrome's present-day pinch constants (2.0, 1.2) are from older code-review snapshots; grida.co analysis is third-party.
- Apple Core Animation rasterization cache eviction timings and CATiledLayer details came from memory/secondary notes. Freeform internals: no public information.
- Flutter per-frame cache limit default value and whether newer DisplayList cache keeps threshold 3: only the header's constructor default and the "3" in older snapshots were seen.
- Miro, Lucid, Cairo-specific, and Figma tile internals: no primary data found.
