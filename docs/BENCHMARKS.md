# Benchmarks

`qraw-bench` (`tests/bench/`) has two parts:

- **Model benchmark.** Timings of load, save, page view, export, hit testing and the main edit operations on generated documents of 1,000, 10,000 and 50,000 cells.
- **Canvas paint benchmark** (`--paint`, `--paint-synthetic`). Frame times of the editor canvas (`ui::CanvasView` over a real `DocumentSession`) while it opens, repaints, pans, zooms, hovers, selects, drags and edits.

All documents are generated by the benchmark from fixed seeds; nothing else is needed to reproduce the figures. They come from one Release run on the machine below, so read them as orders of magnitude and compare them only with runs on the same machine.

Machine of the recorded numbers: 13th Gen Intel Core i7-13700KF (24 threads), 31.1 GiB RAM, Fedora Linux 44, GCC 16.2.1, Qt 6.11.2 with the `offscreen` platform, Release build, commit 802539a with the documentation changes of the public release (no code changes that affect the figures).

## Running it

```sh
cmake --preset release && cmake --build --preset release -j6
export QT_QPA_PLATFORM=offscreen
build/release/tests/bench/qraw-bench --sizes 1000,10000,50000 --repeat 3 --markdown   # model benchmark
build/release/tests/bench/qraw-bench --paint-synthetic --markdown                      # canvas paint benchmark
```

| Option | Meaning |
|---|---|
| `--sizes N,N,...` | cell counts of the generated documents (default `1000,10000,50000`, minimum 100) |
| `--repeat N` | runs per operation or scenario, medians (and for the model benchmark minima) are reported (default 3) |
| `--ops all\|GROUP,...` | `load save semantic pageview png scene hittest move duplicate delete group ungroup`; `move`, `duplicate`, `delete`, `group` and `ungroup` each report the edit and its undo, `hittest` reports three rows |
| `--with-scene` | keep a `DiagramScene` alive on the session during the edit operations, so they include the canvas update |
| `--write DIR` | write the generated documents to `DIR/bench-<N>.drawio` (and `bench-images.drawio` for `--paint-synthetic`) to reproduce a run in another tool |
| `--paint FILE`, `--page N` | canvas paint benchmark on page N (0-based) of FILE; `qraw-cli --info FILE` lists the pages |
| `--paint-synthetic` | the same on the generated image-heavy document |
| `--viewport WxH` | viewport size, default 1600x1000 |
| `--zoom Z` / `--fit` | zoom at the start of every scenario (1 = 100 %, the default), or Fit Window (all content in view, at most 100 %) |
| `--at X,Y` | scene point placed at the top left corner at the start, default the page origin |
| `--scenarios a,b` | run a subset (`open firstPaint fullRepaint pan zoomStep zoomContinuous hover selectionChange dragLift dragMove resizeMove dragMany dragManyLive dragManyBitmap dragCommit editCell memory`) |
| `--frame-scale F`, `--no-warmup` | fewer frames per scenario, skip the untimed warm-up pass |
| `--timers` | enable the scope timers and print the attribution (also `QRAW_PAINT_TIMERS=1`; `QRAW_TRACE=out.json` writes a Chrome Trace Event file for <https://ui.perfetto.dev>) |
| `--no-lod` | switch the level of detail off, to measure what it saves |
| `--json OUT` | write everything as JSON, to compare two runs |
| `--check-budgets`, `--no-time-budgets` | check the report against `tests/bench/paint_budgets.h` (synthetic document only), exit 1 on a violation; the second skips the wall-clock budgets (also `QRAW_BENCH_TIME_BUDGETS=off`) |
| `--markdown` | print the tables as Markdown |

The tool warns when the build type is not Release (the `dev` preset is a Debug build) and exits 1 when an operation fails. It sets `QT_SCALE_FACTOR=1` itself: the figures and counter ceilings are for a device pixel ratio of 1. The commit in the machine block is the one at configure time, so re-run `cmake` after switching commits.

## Model benchmark

### The documents

`tests/bench/generator.cpp` builds one page with exactly N cells, the same bytes on every platform (own PRNG): about 65 % vertices and 35 % edges.

- Vertices on a roughly square grid: rectangle, rounded, ellipse, rhombus and the stencil shape `mxgraph.flowchart.document`; about 20 % carry an `html=1` label with `<b>` and `<br>`, the others a plain label.
- Every 50th grid slot is a swimlane with three children.
- Two to seven small tables (`shape=table` with two rows of two `partialRectangle` cells).
- Edges between grid neighbours, one third each: `orthogonalEdgeStyle`, `elbowEdgeStyle`, and a straight edge with a waypoint.

File sizes: 224 KiB (1k), 2.2 MiB (10k), 11.1 MiB (50k).

### What is timed

| Row | Operation |
|---|---|
| load | `format::readDocument` of the bytes |
| save | `format::writeDocument`; the bytes must equal the original |
| semanticEqual | `format::semanticEqual(original, saved)`, which parses both |
| pageView | `render::PageView::build` of the page |
| exportPng | `render::exportPage` to PNG with a scale that makes the long side at most 4096 px; it builds its own page view, so this includes pageView |
| scene | `ui::DiagramScene` over a `DocumentSession`: the page view, the record of every cell (the snapshot) and the hit grid |
| hit.cellsAt, hit.cellsInRect, hit.snapMove | on a scene of the document: `cellsAt` (tolerance 4) at 10,000 pseudo-random points, `cellsInRect` for 200 rectangles (up to 20 % of the page) and the whole page, `Snapper::snapMove` 200 times; the detail line carries a checksum of the answers |
| group, ungroup | select all, `actions::group`; for ungroup the group is made first (untimed) and the timed step is `actions::ungroup`; both with their undo, and the bytes must equal the original after the last undo |
| move, duplicate, delete | select all, then `ops::moveCells` by (10, 10), `actions::duplicateSelection`, `actions::deleteSelection(includeEdges)`; the session has no canvas unless `--with-scene` is given |
| `.undo` rows | one `DocumentSession::undo()` after the edit; afterwards the saved bytes must equal the original, otherwise the operation fails |

### Reading the numbers

- File and model operations (load, save, semanticEqual, pageView) scale about linearly: 50k cells load in 0.3 s and save in 0.06 s. Load and semanticEqual parse XML (`QXmlStreamReader`); semanticEqual parses both files.
- **exportPng** is the slowest read-only operation (3.5 s at 50k) and grows slowly with the cell count because every size renders a bitmap of about 4096 px: at 1k cells it already costs 0.3 s, so much of it is the size of the image. Export runs on the direct renderer, not on the tiles of the canvas.
- **move** touches geometry only. With a live scene it re-records the moved cells and takes several times longer (1.5 s at 50k).
- **duplicate** at 50k takes 1.2 s: it encodes and decodes the cells and inserts 50k new ones.
- **delete, group and ungroup** are a fixed number of bulk primitives (`ReplaceCells`, one-pass `ReorderCells`, D-036), not one change per cell.
- The **scene** build grows faster than linearly (13 times for 5 times the cells) because of cache effects of an 11 MB document and of the label caches (the label metrics cache holds 16,384 labels, a 50k page has 32,000).

## Canvas paint benchmark

### Scenarios and metrics

A **frame** is the input or edit a scenario performs, together with the paint it causes: the events it posts are processed (the paint that `update()` queued happens there) and, if nothing painted, a synchronous `viewport()->repaint()` follows; all of it is timed. The platform is `offscreen`, so the paint goes to the widget's backing store and no window system flush is measured: on a real desktop a frame costs a little more. Every scenario starts from the same state (zoom, scroll position, no selection, no gesture, one unmeasured paint) and cleans up after itself (edits are undone).

| Scenario | What it does | Frames |
|---|---|---:|
| `open` | read the file, `format::readDocument`, `DocumentSession`, `CanvasView` with its scene (the whole file is parsed, not only the page) | 1 |
| `firstPaint` | the first paint of the start view after the window was shown (once per process, cold) | 1 |
| `fullRepaint` | `viewport()->repaint()` of an unchanged view | 20 |
| `pan` | 40 px scroll-bar steps: right, down, left, up, 15 frames each | 60 |
| `zoomStep` | `zoomIn()` then `zoomOut()` alternately (the view's own steps) | 20 |
| `zoomContinuous` | `setZoom` by a factor of 1/1.03 per frame anchored at a viewport point, then 60 frames of 1.03 back in | 120 |
| `hover` | synthetic mouse moves along a path over the visible cells and around the handles of the first, which is selected | 100 |
| `selectionChange` | the first 50 cells (visible ones first) selected one after the other | 50 |
| `dragLift` | press on an image (else any visible) vertex, one mouse move past the click tolerance: the lift; `settle` is the time until the tiles under the lifted cell are final | 1 |
| `dragMove` | press on an image (else any visible) vertex, a first move that lifts it (not measured), 60 mouse moves of (3, 2) viewport px | 60 |
| `resizeMove` | an image (else any visible) vertex selected, its bottom-right handle dragged: a lift, then 60 moves | 60 |
| `dragMany`, `dragManyLive`, `dragManyBitmap` | every visible vertex (at most 300) selected and moved, with the default replay budget, live replay always, a bitmap always | 60 |
| `dragCommit` | the release that commits the move, and the paint after it | 1 |
| `editCell` | `DocumentSession::edit` setting `fillColor` on one vertex, and the paint after it | 20 |
| `memory` | peak resident set (`VmHWM` of `/proc/self/status`) and the current one, "n/a" off Linux | - |

Per scenario: `frames`; `avg`, `p50`, `p95`, `p99`, `max` in ms; the share of frames over 16.7 ms (60 Hz) and over 8.3 ms (120 Hz); `worst1s`, the worst share of over-budget frames in any sliding window of one second of frame time; `settle`, the time from the last frame until `CanvasView::isRenderIdle()` (the asynchronous tiles are final). Medians over `--repeat` runs are taken per metric. One-frame scenarios show their single time in every column.

### The documents

- **Synthetic image-heavy** (`--paint-synthetic`, `tests/bench/image_fixture.cpp`): an image-heavy document generated from a fixed seed. One page with 150 cells counting the root and the layer (119 vertices, 29 edges). 32 vertices are PNG screenshots of 1000x600 px (RGBA, 8 bit; smooth colour fields with seeded noise and flat panels of text-like blocks, so that each payload compresses to about 1.2 MB of base64), stored the way draw.io stores them (`image=data:image/png,<base64>` inside the style string); the file is 36.9 MiB. The other cells are a mix of shapes, texts, a swimlane, a table, stencil shapes and edges, spread over a board of 8 x 5 slots 1100 x 750 px apart. It stresses what large pictures embedded in a diagram do to the editor: parsing megabytes of style text, decoding and scaling images, and keeping memory in check.
- **Generated 10k cells** (`--sizes 10000 --write DIR`, then `--paint DIR/bench-10000.drawio`): the document of the model benchmark; no images, 6,494 of 10,000 cells carry a label.

### Work counters

Counters (`render/stats.h`) count operations, not time, so a CI gate on them cannot flake. They are relaxed atomics that are always compiled in; the benchmark resets them before a scenario and prints them per frame (and in `--json` as totals).

| Counter | Counts |
|---|---|
| `cellsPainted`, `labelsPainted` | `SceneRenderer` shape and label paints; these happen when a cell is recorded, not when it is painted |
| `textLayouts` | `QTextDocument` layouts created (a miss of the label layout or metrics cache) |
| `imagesResolved`, `imagesDecoded`, `bytesDecoded` | image resolutions (base64 or file), decodes and the encoded bytes of both; once per distinct image |
| `imageScales` | raster images drawn at a size other than their own |
| `pageViewBuilds`, `pageViewUpdates` | full builds and in-place patches of the page view |
| `viewportFullUpdates` | whole-viewport update requests (zoom, page switch, an overlay change whose bounds a handler cannot report) |
| `largeValueCopies` | shared buffers (values of 16 KiB or more, `core::SharedValue`) allocated by copying bytes |
| `recordsBuilt` | cell display lists recorded |
| `tilesRasterized`, `tilesRasterizedSync`, `tilesBlitted`, `tilesSubstituted`, `tilesDiscarded` | tiles rasterised (on any thread, or on the GUI thread while a frame waited), copied to the viewport, drawn from an older or neighbouring tile, and dropped |
| `cellsReplayed` | cell records replayed onto a raster target |
| `cellsSkippedLod`, `labelsSkippedLod` | cells and labels the level of detail skipped |
| `activeReplayed`, `activeBitmaps`, `activeBitmapsDrawn` | cells of the active layer replayed live, interaction bitmaps built and drawn |

### Scope timers

`render/perf_scope.h` has `QRAW_PERF_SCOPE(name)` in the paint path: one relaxed atomic load when off. When on it records, per thread, the call count, the inclusive wall and thread CPU time and the self time. The scopes nest as `ViewPaint > {TileRaster > {SceneBackground, Raster, Text*, Image*}, Composite, Foreground}`, and on the edit path `PageViewBuild`, `DiffViews` and `Record > ShapePaint, LabelPaint`. Each scope costs about 0.5 us when on, which adds around 10 % to a repaint of a 10k-cell page: the shares of the small scopes are overstated by that constant.

### The `bench_paint` gate

CTest `bench_paint` (label `bench`) runs `--paint-synthetic --repeat 1 --no-warmup --frame-scale 0.25 --check-budgets`: about 13 s in dev and 8 s in release. `tests/bench/paint_budgets.h` holds both gates in one table:

- **Counter ceilings** (exact; the real gate): per scenario and counter, a ceiling per frame in units of a constant, of the visible images or cells at the start, or of the images or cells of the page. Image decodes, text layouts and large-value copies are 0 per frame for every scenario that repaints what it has already painted (`fullRepaint`, `hover`, `selectionChange`, `dragMove`, `dragCommit`, `editCell`); `pan`, `zoomStep` and `zoomContinuous` pay at most once per page image and cell; `pageViewBuilds` is 0 for pan, zoom, hover, selection and drag. Counters that count worker-thread work are loose, because they depend on how far the workers got.
- **Time budgets** (a loose smoke test): about 3 times the Release p95 of the table in `paint_budgets.h`, times 3 in a Debug build, times `QRAW_TEST_TIMEOUT_SCALE`. They are a statement about one machine and a small sample, so they are skipped on hosted CI runners (`--no-time-budgets` or `QRAW_BENCH_TIME_BUDGETS=off`, set by `.github/workflows/ci.yml`); a local `ctest` keeps them on.

## Layouts

The std-only layouts of `commands/layout_graph.h` run on the plain graph, with no document. Timed by `tst_commands_layout_flow` (pure layout calls, single thread), Release / Dev (Debug):

| Layout | Input | Release | Dev |
|---|---|---|---|
| `flowLayout` | 500 nodes, 993 edges (random DAG, edges up to 30 nodes ahead, so many dummies) | 7 ms | 35 ms |
| `organicLayout` | 300 nodes, 449 edges (spanning tree plus 150 random edges) | 180 ms | 600 ms |
| `treeLayout` | 1000 nodes | about 1 ms | |

The test fails above 1 s in Release and 20 s in Debug. Organic is O(n^2) per iteration with 20 sqrt(n) iterations (346 for 300 nodes), so 1000 nodes would take about 2 s; the pair loop is not spatially indexed.
