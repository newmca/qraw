# Decisions

Each entry records what was decided and why. Newest at the bottom.

## D-000 Scope

Qraw is a local-first, native replacement for draw.io Desktop. **Excluded:** cloud storage and sync (Google Drive, OneDrive, Dropbox, GitHub, GitLab, ...), accounts and OAuth, plugins, online shape or image search, AI features, real-time collaboration, and a web or browser build. Everything else draw.io Desktop does with local files is in scope, prioritised by ROADMAP.md.

## D-001 Attributes are the source of truth

Modeled elements store their ordered attribute list as raw strings. Typed accessors parse on demand and setters edit in place. **Why:** this preserves unknown attributes, attribute order and the exact number formatting for free, so nothing lossy can happen between load and save. Parsing on demand costs little next to rendering.

## D-002 Two-phase reading

Bytes go into a generic `XmlNode` tree first (`format::parseXml`), and only then onto the model (`format::fromXml`). Writing builds the tree and then serializes it. **Why:** the tree can hold any construct, the model code never touches the XML API, and semantic comparison reuses the same parser and tree.

## D-003 Indentation is not content

Whitespace-only text is dropped from an element if its other children are only elements, comments or PIs. Any other text (mixed content, CDATA, whitespace in a text-only element) is kept exactly. The writer indents element-only content by two spaces and writes everything else verbatim. **Why:** draw.io files are pretty-printed or compact depending on the version. Treating indentation as formatting makes saves deterministic and byte-stable, and real text content is never altered.

## D-004 Output style

The output matches draw.io Desktop's uncompressed files: two-space indentation, `<a />` with a space before `/>`, and attribute values escaping `& < > "` plus `&#xa;`, `&#xd;` and `&#x9;` for newline, CR and tab. Inside compressed payloads the XML is compact (`<a/>`), as draw.io writes it. The file ends with a newline. The output is always UTF-8. A source declaration keeps its version and standalone attributes, and its encoding is rewritten to `UTF-8`.

## D-005 Compressed pages are re-encoded

A compressed page is re-serialized and re-compressed on every save (zlib, default level, raw deflate) instead of reusing the original base64. **Why:** keeping two representations of a page in sync is error-prone, and the model is the single truth. **Consequence:** the compressed bytes depend on the zlib implementation. They are deterministic for one build, but zlib and zlib-ng can produce different (equally valid) output.

## D-006 Undecodable pages are kept verbatim

If a `<diagram>` payload cannot be inflated or parsed, the page becomes `PageEncoding::Opaque`. Its content is preserved and written back exactly, and a warning is reported. The page shows no cells. **Why:** "unknown is kept, never dropped" also applies to data we cannot decode.

## D-007 Cell wrappers

Any `<root>` child element that has an `<mxCell>` child is a wrapped cell, whatever its tag (`object`, `UserObject`, or a custom one). This matches mxCodec. The wrapper owns `id` and `label`. New custom attributes go before `id`, which stays last as draw.io writes it.

## D-008 Unknown root element is an error

A file whose root is neither `<mxfile>` nor `<mxGraphModel>` (for example SVG) fails to load with an error. Unknown content inside a draw.io document never fails. **Why:** such a file is a different kind of file, not a draw.io diagram with extensions. An `<mxlibrary>` root fails the same way, but with the recognisable diagnostic `format::kLibraryDiagnostic` (`LoadedFile::isLibrary`); `DocumentController::openPath` checks the file first and emits `libraryFileRequested`, so the window opens it as a shape library in the palette (`format::parseLibrary`) without touching the open document.

## D-009 Generated ids

`Page::generateId()` returns the smallest unused decimal id starting at 2 (draw.io reserves "0" for the root and "1" for the default layer). **Why:** deterministic and readable, and unique per page as required. Cross-page uniqueness for paste is a concern of the paste operation.

## D-010 Corpus check compares against the original

The round-trip test checks `original ≡ save(load(original))` semantically. It also checks reload equality and byte stability of the second save. **Why:** comparing two of our own outputs would hide symmetric losses. Comparing with the source file catches any construct the codec drops.

## D-011 One CLI implementation, two binaries

The command-line logic lives in the `qraw_cli` library. `qraw-cli` is the headless binary (it defaults to `QT_QPA_PLATFORM=offscreen`). `qraw` dispatches to the same code when it sees a CLI flag, before it creates a `QApplication`.

## D-012 Architecture enforced by the build

`qraw_forbid_qt()` walks the link graph of `qraw_core` and `qraw_commands` and fails the configure step on any `Qt*::` dependency.

## D-013 zlib on Windows from vcpkg

Qt bundles zlib but does not export it for third-party linking. On Windows, CI therefore installs zlib with vcpkg and uses the vcpkg toolchain file. Linux and macOS use the system zlib.

## D-014 Globbed sources and auto-registered tests

Modules collect their sources with `qraw_glob_sources()` (`file(GLOB CONFIGURE_DEPENDS)` of `src/<module>/*.cpp`). Every `tests/<module>/tst_<name>.cpp` becomes the test `tst_<module>_<name>` through `qraw_add_module_tests()` (`cmake/QrawTargets.cmake`). **Why:** a new source or test file needs no edit of a shared CMakeLists.txt, so parallel branches do not conflict. `CONFIGURE_DEPENDS` re-runs the glob on every build, so a new file needs no manual reconfigure.

## D-015 Mutations are snapshot primitives

Every change to the model is one of ten primitive commands (`commands/primitives.h`): insert/remove/replace/replace-many/reorder a cell (`ReplaceCells` is the tenth, D-036), insert/remove/move a page, replace page attributes, replace the document header. Each one stores whole values (a `Cell`, a `Page`, attribute lists) and exact entry positions, and captures its "before" state when applied. Operations (`ops_*.h`) only compose primitives inside a `Transaction`. **Why:** undo followed by redo must give a byte-identical save. With snapshots, this property has to be proven only for these few classes, and the operations cannot break it.

## D-016 Entry-level positions in core

`Page::entryIndex`/`insertCellAt` and `Document::pageEntryIndex`/`insertPageAt` address positions in the raw entry lists. **Why:** foreign `XmlNode`s are interleaved with cells in `<root>` and with pages in `<mxfile>`. Restoring by z-index among cells would put a cell back on the wrong side of a foreign node, and the save would no longer be byte-identical.

## D-017 Pages by index, cells by id

Commands address a page by its index into `Document::pages()` and a cell by its id within that page. Commands are applied and reverted strictly in sequence, so every index resolves against the state it was computed on. **Why:** page ids can be missing or duplicated in real files, while cell ids are the stable keys that draw.io uses itself. Duplicate cell ids resolve to the first occurrence (`Page::validate` warns about them).

## D-018 Operations are free functions; `Editor::edit` is the only entry point

The UI runs `editor.edit(name, [&](Transaction& tx) { return ops::x(tx, ...); }, mergeKey)`. The Editor has no method per operation. **Why:** a new operation never touches the Editor. Operations nest through transaction savepoints.

## D-019 Coalescing by merge key and an explicit break

Consecutive edits with the same non-empty merge key are merged into one undo entry when the command groups have the same shape (`CommandGroup::canMergeWith`). Merging stops at `UndoStack::mergeBreak()`, an undo, the clean state, a key change, or an optional time window. **Why:** a drag delivers live updates to observers at every step but leaves a single undo entry. The UI ends the gesture explicitly instead of relying on timing.

## D-020 Qt-free geometry library

Perimeters, edge routing, path building and label placement live in `qraw_geometry` (`src/render/geometry/`, namespace `qraw::geometry`), which links only `qraw_core` and is checked by `qraw_forbid_qt`. **Why:** the canvas, hit testing and future layout code need the same numbers as export, without depending on QPainter or QColor, and the geometry is unit-testable with exact values. It sits inside `src/render` because only rendering and the canvas use it.

## D-021 Own canvas interface and SVG writer, not QSvgGenerator

Painters target `render::Canvas`, a call-for-call mirror of draw.io's `mxAbstractCanvas2D`. It has two backends: `PainterCanvas` (QPainter, used for the screen, PNG, JPEG and PDF) and `SvgCanvas`, which writes SVG text itself. **Why not QSvgGenerator:** it flattens the output into anonymous paths. It loses the per-cell `<g data-cell-id>` structure, cannot write HTML labels as `<foreignObject>`, positions text with the local font metrics (so output differs between machines and golden tests break), and cannot set the root `content` attribute that makes a `.drawio.svg` editable. Mirroring `mxAbstractCanvas2D` also lets upstream shape and stencil code be ported line by line.

## D-022 Stencils vendored in draw.io's packed form

The 204 stencil sets come from upstream `js/stencils.min.js`. A tools script strips the JavaScript and stores the base64-decoded packed blobs in `resources/stencils/stencils.bin` (about 2.9 MB), along with a `key → set` index (`index.tsv`). C++ ports the small decoder and decodes a set on first use. **Why:** the packed form is half the size of deflated XML (about 6.0 MB), and both need a decoder or inflater at runtime anyway. No JavaScript is vendored or executed. Upstream `stencils/LICENSE` (the Atlassian field-of-use restriction) ships beside the data.

## D-023 Font-independent SVG export

SVG labels are written as draw.io writes them: a `<foreignObject>` with the HTML, plus a `<text>` fallback that is not measured. Export bounds use a deterministic text-extent estimate (`geometry::estimateTextExtent`), not font metrics. **Why:** viewers lay out HTML labels themselves. Without measuring, the SVG output is byte-identical on every machine, which keeps the golden tests stable. Raster and PDF output measures with the real fonts.

## D-024 Embedding the diagram in exports

`--embed` writes the whole document with uncompressed pages (draw.io's current default). SVG gets it in the root `content` attribute, and PNG gets a `tEXt` chunk named `mxfile` holding `encodeURIComponent(xml)`, placed before the first `IDAT`. PDF gets an Info `/Subject` literal string added by an incremental update, because `QPdfWriter` has no Subject setter. draw.io reads all three. The PDF 1.7 EmbeddedFile variant is read but not written.

## D-025 Incremental parent, source and target indexes in `Page`

`Page` keeps, next to the id index, three maps from an attribute value to the ids of the cells that carry it, each list in z-order (ascending entry index, found by binary search). `addCell`, `takeCell`, `insertCellAt`, `appendEntry` and the new `replaceCell` keep them exact; `ReplaceCell` now writes through `replaceCell`. `children`, `childIds`, `childPosition`, `descendants` and `connectedEdges` read them. **Why:** `descendants` built a parent map and `children` scanned all entries on every call, and the commands call them per cell, so select-all operations on 5000 cells took 4 to 6 s. A read-only snapshot passed through the loops was rejected because insertions invalidate cell pointers and entry positions mid-loop. **Rule:** nobody changes id, parent, source or target through the non-const `findCell` pointer. Cells with a duplicate id are not listed (they are not addressable either). Entry insert and remove stay O(n); `ops::removeCells` avoids the cost by removing back to front (delete on 50k cells went from 30.9 s to 0.25 s), while group and ungroup still pay it, so a bulk reorder primitive is the next step if they matter.

## D-026 Union handles for multiple selected cells are on

Upstream's `Graph.multiSelectionHandlesEnabled` defaults to false (Graph.js ~8705). Qraw enables the behaviour always: KNOWN_ISSUES asked for resize and rotate handles on a multi-selection, and the per-cell handles were already hidden for it. The box and the commit follow `Graph.getMultiSelectionCells`, `scaleCellsToBounds` and `rotateCellsAround` (`src/commands/ops_transform.*`, `VertexHandles::forMultiSelection`). **Differences:** the preview outlines the selected cells only, not their children or layouts; `transparentBounds` groups with a child layout are not moved; font size defaults for Ctrl-scaling come from the stylesheet value 12, not `mxConstants`.

## D-027 Sketch and comic rendering is clean-room and deterministic

`sketch=1` and `comic=1` are drawn by `render::SketchCanvas`, a Canvas decorator applied by `SceneRenderer::paintShape` (vertices and edges, screen and export). Comic is a port of HandJiggle; rough is a simplified own implementation that follows the options draw.io passes to rough.js (fillStyle, hachureGap, hachureAngle, fillWeight, bowing, curveFitting, jiggle as roughness, disableMultiStroke). rough.js is not vendored and is never fetched, so the strokes are not identical to draw.io's. **Randomness:** a mulberry32 PRNG seeded from the cell id with draw.io's own 31-hash (rough.js is seeded the same way upstream). Comic mode in draw.io uses `Math.random` and differs on every render; Qraw seeds it too, so a cell looks the same on every repaint and exports are byte-stable (golden tests, no flicker on the canvas). The cost is that two cells with the same id on different pages look alike.

## D-028 Mutation fuzz harness instead of libFuzzer

`tests/fuzz/qraw-fuzz` mutates corpus seeds with its own PRNG (xoshiro256** seeded by splitmix64, plain modulo range reduction) and runs five parsers (XML codec, compressed pages, style, stencil, HTML sanitizer) against their invariants. **Why:** the toolchain is GCC only (no clang, so no libFuzzer), and the CI runners and developers use three platforms. A harness of our own gives the same inputs for the same `--seed` everywhere, needs no instrumentation, and runs as an ordinary CTest entry. Each iteration draws from a PRNG derived from (seed, target, iteration), so `--dump TARGET:ITERATION` regenerates any input without replaying the run; no file is written per iteration, a crash handler reports the iteration and saves the input. **Cost:** no coverage guidance, so it finds shallow bugs (depth limits, bad numbers, malformed structure) quickly and deep ones slowly; run it under the `asan` preset for memory errors. Minimized crashers are kept as regression fixtures (`tests/fuzz/regressions/<target>/`).

## D-029 Default styles are application settings

"Set as Default Style" (draw.io `currentVertexStyle` / `currentEdgeStyle`) is stored in the application settings (`AppSettings::defaultStyles`, as style strings), not in the document, and the merge is a pure function in `src/commands` (`commands/default_style.h`) so the UI and the Insert actions share it. **Why:** draw.io keeps the current style in the editor, not the file, so a saved diagram never carries it, and the lossless round trip is untouched; the helper is testable without Qt. **Cost:** the defaults are shared by every window and survive a restart (draw.io forgets the vertex default on reload), and there is no undo for setting or clearing them. Only the explicit action sets them; draw.io's tracking of the last edited style is not ported.

## D-030 Large values are shared buffers; images and labels are decoded and laid out once

Values of 16 KiB or more in a cell's attributes, in a parsed `core::Style` token and in a `render::StyleMap` are `core::SharedValue`s: an immutable `shared_ptr<const Buffer>`, so copies (undo snapshots, clipboard, duplicate, `ResolvedStyle`) cost a reference count; `str()` and the implicit conversions keep the accessors returning `const std::string&` and `string_view`, setting a value replaces the buffer (D-015's snapshot semantics hold), and the `.drawio` bytes are unchanged. The buffer memoises its content hash and, for a style attribute, the parsed `Style` (`Cell::style()`), so nothing re-parses or re-hashes a megabyte. The renderer keeps decoded images in `render::ImageCache`, keyed by that hash (data URIs) or by absolute path, size and modification time (files), together with the resolve limit: level 0 premultiplied ARGB32, mip levels built lazily with a hand-written 2x2 box filter, SVGs rasterised per power-of-two size, a byte-budget LRU (256 MiB, `QRAW_IMAGE_CACHE_MB`, a hard limit at twice that) that evicts cold images, then unused mip levels, and never an image used in the current frame (`beginFrame()` from the canvas), and one decode for concurrent requests. Labels are laid out once per key in a per-thread LRU of `QTextDocument`s, with the thread-neutral metrics in one shared cache. **Why:** the diagnosis: 92 to 97 % of a frame on image-heavy diagrams was resolving, decoding and rescaling the same images, and 35 % of a text-heavy frame was laying out the same labels; the cache is thread-safe because tiles are rasterised on worker threads. **Cost and alternatives:** a large style exists twice in memory (the attribute and the parsed token); sharing slices of the attribute buffer would avoid it but `std::string&` accessors cannot return a slice, so it would need a rope-style attribute. Exports and prints stay on the exact path (QPainter's own scaling of the decoder's image, because QPainter rounds a downscale of non-premultiplied ARGB32 differently from the premultiplied level 0, by up to 5 levels), so only on-screen pixels change; the entry keeps the decoder's image until the first on-screen use converts it. Decoding at reduced size is an option for JPEG only (`QImageReader::setScaledSize` uses libjpeg's DCT scaling); the PNG handler has no scaled decode, so it is not built. `QPixmap` and `QIcon` stay out of the render code; thread-local caches that hold Qt objects are cleared before the application object goes (`app_exit_cleanup.h`).

## D-031 CPU compositing now, a GPU compositor seam later

The canvas presents a frame through `render::Compositor` (`render/compositor.h`): a `FrameDescription` of the visible tiles (key, version, the immutable `QImage`, destination in viewport device pixels, source rectangle), the items of the active layer (a record plus a transform, or a bitmap plus a transform) and an optional overlay callback. `CpuCompositor` implements it with `QPainter` on the viewport: tiles are copied with `drawImage` at integer device positions in `CompositionMode_Source` (they are opaque), which is the memcpy blit path. **Rules that keep the seam replaceable:** tiles are immutable once published, so a GPU backend uploads one texture per (key, version); every resource is an argument of the call; the only `QPainter` in the interface is the overlay callback; no global state. The overlay (selection, handles, hover, guides, rubber band) stays vector code painted by the interaction layer, and `CanvasView` paints it from `drawForeground` so that the label editor's proxy widget sits between content and overlay. **Why not a GPU compositor now:** the measured cost of the CPU blit is small (a full 1600x1000 frame of tiles takes about 1 ms, see docs/BENCHMARKS.md), while the workload was dominated by decoding and rasterising, which the caches and tiles remove; a GPU path would add a platform dependency (`QRhiWidget` needs Qt 6.7, the project minimum is 6.5, so it would sit behind a version check) and a second code path to keep pixel-identical, for a cost that is no longer on the critical path. Vulkan through QRhi is assumed available when that day comes (Metal and Direct3D through the same API elsewhere); the swap is a new `Compositor` and a texture cache keyed by tile version. **Cost:** every scroll or zoom blit is a CPU copy of the exposed area, and text in tiles is antialiased in grayscale (Qt uses LCD antialiasing only on widget devices), so canvas text is slightly different from the pre-tile canvas (exports are unchanged).

## D-032 A per-cell display list is the render IR

Each cell is painted once into a `render::RecordingCanvas`, which keeps every `Canvas` call as a compact op (a tagged struct with up to six inline numbers; paths, colours, gradients, strings, text blocks and image handles in side tables) in a `DisplayList`; replaying it onto any `Canvas` reissues the calls, so a `PainterCanvas` replay is pixel-identical to painting directly (`tst_render_display_list` compares QImage bytes on every golden fixture, and SVG text through `SvgCanvas`). A `CellRecord` holds the list, the exact visual bounds the recording tracked (strokes at full width with cap and miter reach, the shadow offset, rotation, flips, the label at the size of its layout from `labelMetrics`, never smaller than `CellState::paintBounds`) and a cost estimate; an immutable `RenderSnapshot` holds the records in paint order, the page decoration and a uniform spatial grid, with copy-on-write between consecutive snapshots (an edit records exactly the cells the projection diff changed). **Why a list of ops and not `QPicture`:** QPicture measured slower than direct drawing (docs/research/qt-canvas-performance.md), hides its ops, cannot report bounds and keeps no shared references; **why not per-item caches** (`ItemCoordinateCache`, `DeviceCoordinateCache`, `CacheBackground`): a global 10 MB `QPixmapCache` on the GUI thread, blurry or fully re-rendered on every zoom. A recording holds no pointer into the live model, so tile workers can read a snapshot. **Cost:** recording runs the shape logic and the label layout once per change instead of once per paint, on the GUI thread, and a record keeps its ops in memory (about 2 KB for a typical cell, 56 bytes per op); a restack re-rasterises the tiles of the cells that moved without recording anything.

## D-033 Tiles are rasterised on worker threads, scheduled on the GUI thread, at a few zoom buckets

The GUI thread never rasterises content in steady state. `TileScheduler` (`ui/tile_scheduler.h`) owns the `TileCache` and decides everything on the GUI thread; `render::TileRasterPool` (`render/tile_pool.h`) is a dedicated `QThreadPool` (not the global one; `setExpiryTimeout(-1)` because an expired thread loses its font engines and the per-thread text cache, 1.15 ms against 0.011 ms for the first `drawText`; `clamp(idealThreadCount / 2, 2, 8)` threads, `QRAW_RASTER_THREADS` overrides) that runs jobs of an immutable `RenderSnapshot`, a `TileKey` and a cancellation token, and answers every job with a queued call (never a blocking one: deadlocks). Scheduling stays out of the pool so that a re-prioritisation never waits behind stale work: at most two jobs per worker are handed over, the plan (visible tiles of the displayed bucket centre first, a one-tile ring biased to the pan direction, and only when idle and cheap the neighbouring buckets) is recomputed once per event-loop turn, jobs the plan no longer wants are cancelled and stale results dropped. Zoom is quantised to buckets, the view's own steps plus intermediate ones wherever two steps are more than x1.2 apart, so a step blits 1:1; the bucket above a zoom is drawn scaled down by at most 1.2, the tiling on screen stays while a gesture runs (up to 2x), and a settled zoom between buckets gets one transient exact-scale tiling. A tile that is missing or stale is shown from an older version, else from another bucket (scaled); only when nothing exists is it rasterised on the GUI thread (`tilesRasterizedSync`). Small edits (at most 4 visible tiles, estimated under 1.5 ms) are rasterised at once so typing is never a frame late; the new tiles of a larger edit appear together or after one frame. Synchronous mode (`CanvasView::setSynchronousRasterization`) keeps pixels deterministic for the screenshot harness and tests. Per-thread text layout caches mean a label is laid out once per worker that draws it. Alternatives rejected: rasterising in `QtConcurrent::run` per tile (no priorities, no cancellation, the global pool); a coarse low-scale preview pass for jumps to unseen areas (the prefetch ring made a synchronous tile rare enough: 0 per pan frame in Release; revisit if the 0.27 per frame seen in a Debug build shows up on slow machines); admission control for regions that change every frame and idle warm-up of off-screen fonts and mips (not needed for the measured workloads). The threading rules and the table of what a worker may touch are in ARCHITECTURE.md; ThreadSanitizer (libtsan) is not installed here, so races are covered by those rules, a stress test (`tst_ui_canvas_tiles_threaded`) and the asan preset.

## D-034 Cells under the user's hands are a live layer above the tiles; far zoom skips what cannot be seen

A move, or the resize or rotation of one vertex, lifts the cells it changes out of the tile snapshot (`DiagramScene::setExcluded`, `RenderSnapshot::withoutRecords`) into `ui::ActiveLayer`, which the compositor draws above the tiles from the cells' own display lists under a translation (or from a record of the previewed geometry), and as one bitmap when replay is estimated to exceed 4 ms. The tiles under the lifted cells are rasterised again without them once, by the scheduler's ordinary edit policy; the pre-lift tiles are kept (shared images) so cancel restores the picture without rasterising; after the edit the layer lives until the tiles of the new place are ready. Chosen over "paint the lifted cells over the old tiles" (wrong for transparent and shadowed cells) and over a bitmap of everything (resampled, blurry when zoomed, and a bitmap of a big selection can be larger than the screen). The price is that a lifted cell is drawn above everything during the gesture and that a doubled picture shows until the exclusion tiles arrive (3 ms on the image-heavy synthetic document). Edges attached to one lifted cell are re-routed with `PageView::previewEdgeState` (no `PageView::build` per move); child cells of such an edge (labels as cells) and the jumps over other edges are not followed. Level of detail (`render/level_of_detail.h`) is a pure function of a record's bounds and label size and the device scale, applied in replay only: a cell below 1 px in both directions and a label below 4 px are skipped; export, print and thumbnails never use it, so goldens are byte-identical. Multi-selection resize and rotate and the edge handles keep their overlay previews until their previews can be expressed as records too (KNOWN_ISSUES.md).

## D-035 Hit testing reads a spatial grid over the page view, not scene items

`DiagramScene` keeps no `QGraphicsItem` per cell. `cellsAt`, `cellsInRect`, the drop target, the fold controls and the arrows of a hovered vertex ask `DiagramScene::statesIn(rect)` for candidates: a `render::SpatialGrid` (`render/spatial_grid.h`, three uniform grids of 256, 4096 and 65536 units, a rectangle registered in the finest level where it covers at most 64 cells, the rest in a short list that is always scanned, entries sorted by cell key) built from one box per `CellState` (paint bounds with a pixel of slack, rotated bounds and bounds united) with the paint index as the item, so a query returns indices in ascending paint order and the topmost-first answer needs no sort of strings. The exact shape tests are the ones the BSP index served before, and a candidate must still meet the old candidate box, so the answers are identical (a checksum over 10,000 random points, 201 rectangles and 200 snapper moves on the generated 1k, 10k and 50k documents is unchanged, and `tst_ui_canvas_projection` compares both queries with a scan of every state). The grid is rebuilt from the page view after every projection change (about 1 ms at 10k cells) and read-only in between. The `QGraphicsScene` stays for the coordinates and the rotated label editor's proxy widget: `NoIndex`, scene rectangle = the page area. **Why:** the BSP index took 0.46 ms per `cellsAt` at 10k cells and 3.8 ms at 50k (37.7 s for 10,000 points; why was not investigated), against 2.7 and 18 us now, and the per-edit item churn went away. **Not built:** a packed R-tree (not measured: the grid's queries are a few microseconds and its rebuild a few milliseconds); indexing the snapper's scan (guides match on a line, not a distance, so a vertex of any distance can match: it stays a scan of the vertex states, 0.3 ms at 50k cells).

## D-036 Bulk changes: `ReplaceCells`, and a reorder that is one pass over the entries

`ops::groupCells` and `ops::ungroupCells` used one `ReplaceCell` and one `ReorderCells` per cell, and each of those shifted the entry vector and every id's stored position (O(n)), so grouping 50k cells took 94 s and its undo 146 s. `commands::ReplaceCells` replaces many cells in one pass (`Page::replaceCells`; the parent, source and target indexes are updated per cell below 64 re-linked cells and rebuilt once above) and `ReorderCells` now moves any number of entries in one pass (`Page::moveEntries` / `restoreEntries`: only the window between the first and the last position that changes is rewritten, the id index is fixed for that window, the grouped indexes per cell or rebuilt); `ReorderCells::Order::KeepGivenOrder` lets an operation set the order inside the block. Group moves the selected cells with their subtrees behind the new group in one `ReplaceCells` (new parent, geometry made relative) and one `ReorderCells`, then moves the unselected edges between them to their nearest common ancestor, one pair of primitives per target parent; ungroup dissolves the groups of one parent together, in rounds from the outermost. Apply and revert are exact inverses, so byte-identical undo and redo hold (`tst_commands_ops_structure_corpus`, `tst_commands_editor_corpus`, `tst_core_page_bulk`). **Differences from the one-by-one version:** an unselected edge between two grouped cells is moved after all the cells, not after the cell that completed it, so it is drawn above cells that were later in the selection; the edge's geometry is translated against the final position of its new parent, which fixes an offset the old order gave edges moved into a grouped cell. Group 94 s to 0.74 s and ungroup 100 s to 0.69 s at 50k cells with a scene (BENCHMARKS.md). **Why not make `takeCell` and `insertCellAt` cheaper:** positions are an API (`entryIndex`, anchors computed by the operations); an order-statistics tree behind them would touch every reader of `rootEntries()`.

## D-037 An edit that keeps the tree patches the page view in place

When a change set holds only changed cells (nothing added, removed, reordered or re-parented, no page property), `DiagramScene` calls `PageView::update` instead of `PageView::build`: it rebuilds the states of the changed cells and of what depends on them (their descendants, the edges attached to them or to their descendants or, for a collapsed cell, to the cells inside, repeatedly) with the same `Builder` as a full build, runs the line jumps again, and reports the states it rebuilt and what they were, so the projection diff compares only those. It refuses (the scene then builds the view again) when a changed cell is not a state, was hidden, collapsed, expanded or turned into an edge, a dependent cell is not drawn although it is not hidden (an edit might make it drawable), a rebuilt state can no longer be resolved, the edges form a cycle (the result would depend on the order of resolution) or the grid size changed; on refusal the view is left exactly as it was. `tst_render_page_view_update` compares the patched view with a full build state by state for moves of terminals, groups, children, labels that read an attribute of their parent, jumps, collapsed containers and terminal changes, and `tst_ui_canvas_projection` does so after real edits and undo. **Result:** `editCell` on 10,000 cells in Fit Window 83 ms to 6.0 ms per frame (`PageViewBuild` 38.6 ms and `DiffViews` 21.5 ms before, `PageViewUpdate` 0.6 ms and `DiffViews` 0.01 ms now). **Not kept:** the diagnostics of the view that was patched are those of the build it started from (only the export reads them); a structural edit (add, remove, re-parent, reorder, page properties) still builds the view again, 0.25 s at 50k cells.

## D-038 Layouts: a std-only module of pure functions, our own tree and radial algorithms

`commands/layout_graph.h` holds the layouts as pure functions from a `layout::Graph` (node bounds in z-order, edges as node indices) to a `Placement` (new bounds, nullopt for nodes left alone): `treeLayout`, `radialLayout`, `circleLayout`, `findTreeRoots`. `ops_layout_graph.cpp` builds the graph from a page (the visible vertices with a position among the children of a parent, optionally restricted to a selection, and the edges that end at them), runs a function and writes the result back with `ReplaceCell` (vertices that moved; edges that touch a moved vertex lose their waypoints and take the kind's edge style: tree layouts keep it, Org Chart sets `edgeStyle=elbowEdgeStyle;elbow=vertical`, Radial Tree and Circle set `noEdgeStyle=1` as `mxGraphLayout.setEdgeStyleEnabled(false)` does). The menu (`ops::arrangeLayout`) and the `childLayout` values `treeLayout` and `circleLayout` (`ops::applyLayouts`) share it, and so can CSV and Mermaid import. **Sources:** `mxCircleLayout.js` is in the upstream clone and is ported (the Graph.js:12704 wrapper too: circle anchored at 20 / `startSize` + 20, container fitted, transparent parents anchored in place). `mxCompactTreeLayout`, `mxRadialTreeLayout`, `mxHierarchicalLayout` and `mxFastOrganicLayout` are not in the clone, and draw.io's current menu runs ELK (JavaScript) for them, so the tree and radial layouts are written from the documented behaviour (parameters `levelDistance`, `nodeDistance`, `horizontal`, `invert`; root stays in place; sector per leaf count) without copying any outside code. **Tree:** contour packing (each subtree is placed against the contour of the siblings before it, a parent is centred over its first and last child), levels aligned across the forest (a level is as thick as its largest node, `levelDistance` below it), siblings in z-order of the vertices, several roots side by side, first root anchored in place, or the whole forest at an origin (containers). A node reached twice belongs to the first tree reaching it. **Radial:** sectors proportional to leaf count, the first child of the root at the top and the rest clockwise, each ring as far from the last as the nodes' half diagonals plus `levelDistance`, and further out where neighbours on a ring would otherwise touch (nodes are treated as circles of their half diagonal), so the result never overlaps. **Why not port ELK:** it is a large Java library compiled to JavaScript, and exact positions would not be reproducible without it; our layouts are deterministic and tested for the properties users see (centred parents, even levels, no overlap). **Defaults:** tree 30 between levels and 20 between neighbours (`treeLevelDistance` default 30 for the container), Org Chart 40 and 20, radial 40 and 20, circle radius 100. **Not built:** Organic, Flow, Balloon Tree, Mindmap, parallel edges, options dialogs, a layout that follows `invert` from the menu.

## D-039 Layouts II: our own layered and force-directed layouts

`layout_graph.h` gains `flowLayout` (layout_flow.cpp) and `organicLayout` (layout_organic.cpp); `Placement` gains `edgePoints` for layouts that route edges. **Sources:** `mxHierarchicalLayout` and `mxFastOrganicLayout` are not in the upstream clone and draw.io runs ELK (`layered`, `force`) instead, so both are clean-room, written from the textbooks (Sugiyama et al. layering and crossing reduction, Gansner et al. dummy weights, Fruchterman-Reingold) and from the options the draw.io files carry (`Graph.replaceLegacyLayout`: orientation, intraCellSpacing, interRankCellSpacing, interHierarchySpacing, parallelEdgeSpacing, forceConstant); no outside code was copied. **Flow:** cycles are broken by reversing the back edges of a depth-first search in node order; ranks are longest-path, then a node with more links out than in moves down next to its successors (cheaper than network simplex, and keeps sources next to their targets); a link crossing ranks gets one dummy per rank; the order is reduced by 24 barycenter sweeps plus adjacent swaps, keeping the best order seen; positions are not Brandes-Koepf: each rank is moved in turn to the weighted least-squares position next to its neighbours (dummies weigh more, so long edges straighten) under the minimum gaps, solved exactly by pooling adjacent violators, 24 down and up sweeps; ties are decided by node and edge order, so the result is deterministic and independent of the current positions. Components are laid out on their own and stand side by side; locked vertices are left out together with their edges. Routes are orthogonal: they run along the rank axis and bend only in the gap between two ranks; parallel edges between the same two nodes are spread by `parallelEdgeSpacing` (a reverse pair counts as parallel). Menu entries set `edgeStyle=orthogonalEdgeStyle` (draw.io's menu uses ELK-routed polylines, `elkCompat`, which we do not have). **childLayout=flowLayout** follows Graph.getLegacyChildLayouts: `flowOrientation` defaults to `east`, which Graph.getElkDirection maps to LEFT, so by default edges point right to left; north is down, south up, west right. **Organic:** forces act on the gap between node borders (so large nodes keep their room), repulsion k^2/d up to `maxDistanceLimit`, attraction d^2/k, linear cooling, 20 sqrt(n) iterations; the start is a sunflower spiral in node order with seeded jitter (a small LCG, not `std::` distributions) rather than the current positions, so the layout is repeatable and idempotent; a final pass pushes overlapping boxes apart along the line of their centres until 10 apart. **Not built:** `childLayout=organicLayout`, which draw.io also keeps as a legacy value (a layout that moves every child on every edit); options dialogs; `rack`.

## D-040 Insert > Advanced: pure importers that return detached cells, laid out by the layout module

From Text, CSV and Mermaid are functions in `qraw_commands` (std-only, `import_diagram.h`) from text to `imports::Result` (detached `core::Cell`s with parents before children, errors with line and column, warnings), with the layout already applied through the same functions as Arrange > Layout (`layout_graph.h`; the edge routing helper moved to `layout_support.h`) and the top-left corner at the origin. The dialogs only collect text; `actions::insertImported` hands the cells to `insertBundle`, so an import is one undo step with the default style applied and the new top-level cells selected, like a paste. **Why detached cells and not an edit:** the importers are tested without a document, an error never leaves a half-made import, and the same code serves the screenshot harness. **Label sizes** (CSV `auto`, Mermaid nodes) come from a callback (`imports::LabelMeasure`): the UI passes `label::preferredBounds` with the wrapping removed, the unit tests use a character-count estimate, so the commands module needs no Qt. **CSV** is a port of `doImportCsv` without its parts that act on the live graph: rows are not matched with existing cells (no update by `identity`, no data sources), `container` and `list` are not supported, and cell ids are the insertion's. **Mermaid** is not the mermaid library (JavaScript, a browser engine): a hand-written reader of a documented subset, so that unsupported input is an error with a position and never a silent mis-drawing; flowcharts are laid out level by level so that a subgraph is a container that is a node of the level above, sequence diagrams by columns and rows with messages attached at fixed heights (`exitPerimeter=0`, no `sequenceEdgeStyle`). **From Text** has the list type (`EditorUi.parseOutline`) and a diagram type written from the documented behaviour of draw.io's dialog, whose source is not in the pruned clone. **Limits:** 10,000 shapes; the organic layout (quadratic) is replaced by a layered one above 500. **Not built:** PlantUML (needs Java or a server), other Mermaid diagram types, CSV re-import and data sources, remembering the dialog's text.

## D-041 Units are a preference; Edit Diagram replaces the page as one primitive

**Units.** draw.io keeps the unit in the user's settings (`mxSettings.setUnit`, `graph.view.unit`), not in the file, and so does Qraw (`AppSettings::measureUnit`, key `view/unit`): a diagram saved in millimeters opens in points on another machine, as in draw.io, and nothing about it touches the lossless round trip. `ui/measure_units.h` is the one place that converts (draw.io's `Editor.toUnit` / `fromUnit`: 3.937 px per mm, 100 px per inch, precision 3 decimals for inches and millimeters, 4 for centimeters, 5 for meters, typed values rounded to 0.1 px, the grid size not rounded); `LengthSpinBox` (format_controls) is the one field class that uses it. The model stays in pixels. `MeasureUnits::instance()` is the notifier (one preference per process), so the View menu and the Format panel's Units box stay in step. **Deviation:** Points show two decimals and are not rounded to 0.1 px, as the fields did before units existed.

**Edit Diagram.** The page text is `format::pageModelText` and the result `format::parsePageModelText` (both in `codec.cpp`, next to the code that reads and writes a model, so the text is exactly what a file would hold); `commands::ReplacePage` swaps the whole page and records it as removed and added, which `ChangeSet` already folds into "reset", so every observer rebuilds the page. `ops::replacePageModel` keeps what is not part of the model (the `<diagram>` attributes, the encoding, the foreign `<diagram>` children), so an unchanged text gives an identical file. The dialog does not parse text that was not edited.

## D-042 Merged table cells: the hidden cells are the row's, and the table paints collapsed borders

A merged cell is a cell with `rowspan` / `colspan` that the table layout grows over the cells it covers, and the covered cells are hidden (`visible=0`), as draw.io does (`TableLayout.execute`, `Graph.visitTableCells`). Hidden cells are not states of the `PageView`, but the grid needs them: the span arithmetic counts them (the column index of the next cell depends on them), and the line under a merged cell is a gap exactly because they are counted. So a `tableRow` state keeps its hidden children (`CellState::hiddenChildren`: position among the row's cells, bounds, alternate bounds and resolved style), `CellState::alternateBounds` keeps what a cell's single column and row size is (`point` of `visitTableCells` is computed from it, not from the grown geometry), and the children listing the table painter gets (`ShapeChild`) interleaves them, with `visible=false`. An edit that touches a hidden cell is not "a change of visible cells", so `PageView::update` already refuses it and the view is built again. **Layout.** `visitTableCells` exists twice because the model and the view have no common type: `ops::tableCells` (std-only, from the page) and `detail::visitTableCells` (from the children listing); the unit tests pin both to the same rules. One deliberate difference from upstream: `rowLayout` divides by the sum of the cells' single widths (alternate bounds) and not by the width of the visible cells, which is the same number as long as every covered cell exists, and keeps the columns spread when a covered cell was deleted. **Collapsed tables.** `tableRender=collapsed` is the upstream renderer, not an approximation: the table paints the fills and every border of its rows and cells (`shapes_table_collapsed.cpp`, a port of `paintCollapsedTable` and the region and border solving of `Graph.getCollapsedTable*`), each shared border once, the most specific stroke winning; the scene renderer skips the shapes of the rows and cells (`isCollapsedTableChildShape`) so nothing is painted twice. Colours that a row or cell takes from its parent (`strokeColor=inherit`, `parentFillColor`, `parentStrokeColor`) are resolved in that file only; elsewhere `inherit` is still no colour. Not painted: the striping colours and the title's glass effect.

## D-043 Dark diagram mode: the scheme is part of the render context, colours are mapped when the style is resolved

**Where the setting lives.** `mxGraphModel@adaptiveColors` (`auto`, `simple`, `none`; absent means `auto`, `Graph.defaultAdaptiveColors`) is stored as draw.io stores it, after `shadow` (`Page::adaptiveColors`, `ops::PageProperties::adaptiveColors`, the Adaptive colors box of the Diagram tab; `default` removes the attribute as `Editor.js` does). **Whether the diagram is shown dark** is not in the file. In draw.io it is the application's appearance (`Editor.darkMode`, which sets the CSS `color-scheme` that `light-dark()` follows); Qraw's own theme was first independent of the diagram, so View > Dark Diagram was a per-user preference (D-053 replaced it with View > Diagram Appearance, which follows the theme by default; `AppSettings::diagramDark` became `diagramAppearance`, `DocumentSession::setDiagramDark`, a `render::Theme` in the `RenderContext`) and the export dialog has its own "Dark appearance" (`ExportOptions::dark`, `qraw-cli --dark`). **What the page says decides what the scheme does** (`Theme::forPage`, applied in `PageView`): `none` keeps the diagram light, `simple` changes only the colours that name a dark side (`default` and `light-dark(a, b)`), `auto` also inverts every explicit colour.

**The mapping** is `mxUtils.getInverseColor` ported (`render::inverseColor`: invert by 93 %, rotate the hue by 180 degrees, keep the alpha), so white becomes `#121212` (`Editor.darkColor`), black `#ededed`, a pastel fill a dark tone of its hue. `default` colours resolve to `#ffffff` on `#121212` in the dark scheme (`Editor.lightColor`, `Editor.darkColor`) and are not inverted again; `light-dark(a, b)` picks its side (a comma inside `rgb(...)` no longer breaks it); an absent `fontColor` is the inverted black. **Why at style resolution and not in the canvas** (draw.io converts in `mxSvgCanvas2D.getLightDarkColor`): the defaults are `light-dark(#000000, #ffffff)` there, so they never meet the inversion, while a canvas decorator here would see `default` already resolved and invert it to `#ededed`. Resolving once per cell also keeps every consumer (the display lists, tiles, export, SVG, label editor, palette thumbnails) on one path, and a toggle is a rebuild of the page view, which the snapshot diff turns into full damage (`tilesRasterized` rises, the pixels equal a direct dark render, `tst_ui_canvas_tiles`). **Labels:** `adaptLabelColors` rewrites `color`, `background-color` and `<font color>` in the sanitised label HTML (`Graph.addLightDarkColors`). **Page:** the paper is `Theme::pageBackground` (an explicit background is inverted as a colour, an absent one is `#121212`), and the backdrop, page border and grid have dark colours (`PageDecor::dark`). **Exports:** the same scheme; a transparent export stays transparent, and an SVG without a background keeps none.

**Not done:** colours that do not come from the style (the fixed black and white of a few painters, the explicit colours inside stencils, themed SVG images), colour pickers that write a dark variant per swatch (`light-dark` values are read, not written), and `Editor.systemColors`. See KNOWN_ISSUES.md.

## D-044 Freehand: a stencil vertex built from a simplified pointer path

`mxFreehand` is not in the vendored clone, so its stored form could not be checked against a draw.io file: the stroke is a vertex with `shape=stencil(<compressed XML>)` and one `<path>` of quadratic segments (`strokewidth="inherit"`, round caps and joins, `<stroke/>`, never a fill), which every draw.io renders, Edit Shape edits and the cell's size scales. `commands/freehand.h` (std-only) holds the pure part: Douglas-Peucker simplification (iterative, so a long stroke cannot overflow the stack), then a quadratic Bezier through the midpoints of the remaining segments with the points as control points (smooth, and the curve stays in the hull of the points, so the cell's bounds are the extent of the kept points; at least 1 x 1). The UI part is a handler of the interaction layer (`FreehandTool`, priority 10, so a drag draws instead of selecting while it is on): the live stroke is the raw pointer path in the overlay with exact bounds, Escape cancels it, release inserts one vertex through `insertBundle` (one undo step "Freehand", selected afterwards, not snapped to the grid) with the stored default style applied (`applyDefaultStyle`; stroke width 2 when the defaults give none, `fillColor=none`). The tolerance is 2 screen pixels. **Not built:** draw.io's brush window (size, smoothing and Close Path options, pressure), so a stroke takes its width and colour from the default style; closed paths.

## D-045 Scaled displays: device pixels for everything that is drawn, pixel sizes for diagram text, one whole-pixel origin

**Device pixel ratio.** The canvas, the tiles, the active layer and the thumbnails are in device pixels (`scale = zoom x dpr`); logical pixels are for widgets, handle sizes and the scroll bars. At a fractional ratio a scroll offset of whole logical pixels is a fractional number of device pixels, and the tiles are placed at `round(offset x dpr)` (`CanvasView::tileViewport().origin`, unchanged). **New:** the overlay (`drawForeground`: handles, outlines, the rubber band) is drawn from that same whole device pixel (it was drawn from the unrounded one, up to half a device pixel beside the cells under it: 0.25 px at 125 % in the test). The active layer already used it.

**Diagram text is pixels and does not depend on the screen.** Every font of diagram text is built by `render::diagramFont` (a pixel size, never a point size; hinting off) and the documents that lay out labels convert the points of HTML (`font-size: 12pt`, `<font size>`) at 96 dpi through a fixed paint device (`render::configureTextDocument`). Before, glyph hinting followed the screen (Qt turns it off above a device pixel ratio of 1, so `QT_FONT_DPI=120` changed the pixels of a PNG export, and the user's fontconfig settings did too), and a point size followed the platform's logical DPI (72 on macOS, `QT_FONT_DPI` or `Xft.dpi` below 96 on Linux, so a label with `12pt` was 12 px there against 16 px in a browser). Metrics did not change, only glyph pixels and point sizes. `tst_render_font_dpi` exports one file by child processes of `qraw-cli` with several `QT_FONT_DPI` and `QT_SCALE_FACTOR` values and compares the pixels. Hinting off also makes the canvas text at a device pixel ratio of 1 the same as at the other ratios (it was hinted vertically there).

**Tests of pixels compare in device pixels.** A grabbed widget is as large as the widget times its device pixel ratio; a reference painted without the ratio, or a rectangle or search window in logical pixels, is wrong at every ratio but 1. All eight test files that failed under `QT_FONT_DPI=120` were that (or, for `tst_ui_canvas_tiles_threaded`, a start condition that depends on how fast tiles are made: the edit's pass counted the prefetch ring still in flight; for `tst_ui_level_of_detail`, a zoom that was 0.05 device pixels per unit at ratio 1 only), not a fault of the picture: with a reference at the ratio the composited viewport equals the direct render pixel for pixel at 1.25, 1.5 and 2. The screenshot harness writes device pixels, which is now documented (`--size` is in logical pixels). Where the live preview (the active layer's replay) is compared with the tiles at a ratio other than 1 or 2, a per-channel difference of up to 3 of 255 is accepted: the same geometry reaches the rasteriser through different sums and the antialiased coverage differs by rounding; the best integer shift of one image over the other is (0, 0), and `aOneDevicePixelShiftIsStillSeen` proves that a pixel of movement is far above the tolerance. At ratio 1 and 2 the comparison stays exact. The CTest entries `<test>_dpr125` and `<test>_dpr2` (label `hidpi`, `qraw_add_hidpi_variants`) run the sensitive tests under `QT_SCALE_FACTOR` 1.25 and 2 in every preset and in CI.

**Not done:** a real display. The offscreen platform has a device pixel ratio but no compositor and no second monitor with another ratio; the thumbnail refresh on `DevicePixelRatioChange` is exercised with a synthetic event only (KNOWN_ISSUES.md).


## D-046 Application id: io.github.newmca.qraw (all lowercase)

The id was first written with the project name in mixed case (the repository's name in its own casing). `appstreamcli validate --pedantic` reported `cid-contains-uppercase-letter`: the AppStream specification (generic component `<id/>`, https://freedesktop.org/software/appstream/docs/chap-Metadata.html, read 2026-11-26) says the id follows `{tld}.{vendor}.{product}` and that "it is strongly encouraged to only use lowercase letters". Flathub's requirements (https://docs.flathub.org/docs/for-app-authors/requirements, read 2026-11-26) take the form `io.github.<user>.<repo>` for a GitHub project, require the domain part to be lowercase, and require the app id, the manifest name and the metainfo `<id>` to be the same string. The repository is github.com/newmca/qraw, so the id is `io.github.newmca.qraw`.

Renamed: `QRAW_APP_ID`, the three files in `resources/linux/`, the hicolor icon names (PNG and SVG), the metainfo `<id>` and `<launchable>`, the desktop file's `Icon=`, the macOS bundle identifier (from the variable), `QGuiApplication::setDesktopFileName` (from the variable) and the Flatpak manifest. `tst_ui_app_identity` reads the files from the source tree and checks that the variable, `desktopFileName()`, the metainfo `<id>`, the `<launchable>`, `Icon=` and the file names agree, and that the id is lowercase.

**User data is not tied to the id.** Settings (`QSettings`), the recovery folder (`QStandardPaths::AppLocalDataLocation`) and the user libraries derive from the organisation and application names set in `src/app/main.cpp`, not from the id. (Inside a Flatpak they live in `~/.var/app/<id>/`.) No `<replaces>` is needed: no release or package with an earlier id was ever published.

## D-047 Renamed from QtDraw to Qraw because of the Qt trademark

"Qt" is a registered trademark of The Qt Company. Its guidelines (https://www.qt.io/trademark/, read 2026-11-26) allow fair use for an application created with Qt as long as the name is not used in a way that suggests sponsorship or endorsement (1.2), and for tools made for Qt. Under "prohibited use" they list the Qt trademark "in conjunction with your company name or another name without express written permission" (2.3), as part of a company name or logo (2.6) and in a domain name (2.4). ## D-048 Packages: per-machine installer, one binary family in the bundle, deployment by Qt's API

- **Deployment.** `qt_generate_deploy_app_script` plus `install(SCRIPT)` (Qt 6.3+, `windeployqt` / `macdeployqt`), only on Windows and macOS; the Linux install is unchanged, because distributors and the Flatpak bring their own Qt. No hand-written copy steps, so a new Qt module or plugin the app links is picked up. What the tools do not find is listed in `cmake/Packaging.cmake` (zlib, the SVG and JPEG image plugins, SVG icons) and the install fails when a required file is missing, instead of shipping a package that starts and then lacks a plugin.
- **Per machine.** CPack's NSIS template is per machine (administrator rights, Program Files, uninstall entry and file association for all users). A per-user installer needs a custom NSIS template, which is code we would own and cannot test locally; the portable ZIP covers installing without administrator rights. Revisit when someone needs it.
- **File association.** ProgID `<app id>.drawio` with icon and open command; `.drawio` points at it only when no other program is registered (never takes over draw.io Desktop silently), otherwise Qraw is listed under "Open with". The macOS imported type uses the same identifier.
- **CLI in the packages.** Windows: `bin\qraw-cli.exe` beside `qraw.exe` (same DLLs, same `qt.conf`). macOS: `Qraw.app/Contents/MacOS/qraw-cli`, so the bundle is the only thing to install and its Frameworks are shared; the GUI executable also accepts the CLI flags (it is one binary, `src/app/main.cpp`).
- **Not signed.** No certificate or Apple account exists, so nothing claims to be signed or notarised; the ad-hoc signature on macOS only satisfies Apple silicon's rule that code must be signed.

## D-049 Crash reports and recovery: a plain signal handler in `qraw_diag`, no KCrash, no library

- **Why not KCrash, Breakpad, Crashpad or Sentry.** KCrash is a KDE Framework: the plan is plain Qt (docs/research/kde-best-practices.md), the app must also run on Windows and macOS, and the DrKonqi dialog it starts is KDE only. Breakpad, Crashpad and Sentry are third-party libraries (and, for the last two, a separate handler process or a service): the rules forbid a new product library without a decision, a report must never leave the machine, and what a user needs here is a text file to attach to a bug report. A signal handler of a few hundred lines gives that.
- **How.** `diag::installCrashHandler` (`src/diag/crash_handler_posix.cpp`, `..._windows.cpp`) after the application name is set. POSIX: `sigaction` with `SA_ONSTACK|SA_RESETHAND|SA_NODEFER` for SIGSEGV, SIGBUS, SIGFPE, SIGILL and SIGABRT on an alternate stack (so a stack overflow still reports; the stack is per thread, so only the installing thread has it); the handler calls only `open`, `write`, `close`, `time`, `getpid`, `raise` and `backtrace`/`backtrace_symbols_fd`; the header text is built at install time into a static buffer and the folder path is a static buffer, the file name and the UTC time are formatted by hand (`gmtime` is not async-signal-safe: `diag/async_safe_text.h`, tested against Qt); `backtrace()` is called once at install so that libgcc is loaded before it is needed. Then the default action is restored and the signal raised again: systemd-coredump, DrKonqi and ABRT still receive the core. `std::set_terminate` writes the report of an uncaught exception (type and `what()`) and calls `abort()`; the SIGABRT handler sees that the report exists and only re-raises, so there is one report. Windows: `SetUnhandledExceptionFilter` writes the code, the address as module+offset, a best-effort call stack and a `MiniDumpNormal` dump (dbghelp, a system library; no heap, so no document content), then passes the exception on.
- **What a report is not.** It has no document content, no settings, no path of a document. It is a file in the user's data folder; nothing is sent anywhere. Reports of `qraw-cli` are marked (`Process: cli`) and do not trigger the GUI's dialog.
- **Session marker.** `QLockFile` `sessions/<pid>.lock` from start to normal exit, with staleness decided by the owner process being gone (as for the autosave copies, `setStaleLockTime(0)`): a live lock is another running instance and is never taken for a crash; a marker that names the current process id is stale too (the id was reused). The two witnesses of an unclean end are a stale marker and a GUI crash report newer than the last one shown (`AppSettings::crashReportsSeenUntil`). The dialog is also shown when autosaved copies exist, which is what the old per-snapshot question did; with files on the command line it is shown only when a session really ended unexpectedly (a double click on a file should not ask about old copies every time). A killed session with nothing to recover still gets the dialog, with a Close button, because an unclean end should always be reported.
- **Several documents.** A window holds one document, so Recover opens the first copy in the empty window and each other in a `MainWindow` of its own. Quit closes the window it is used in (unchanged).
- **Data folder.** `diag::dataRoot()` is `<GenericDataLocation>/Qraw/Qraw`, the same as `AppLocalDataLocation` of the GUI, but independent of the application name, which differs in `qraw-cli`. `RecoveryStore::defaultDirectory` uses it. Settings and recovery data do not move.
- **Logging.** One `QLoggingCategory` per Qt-using module and subsystem (`qraw.<module>[.<sub>]`, default level info), the log file keeps one run plus the previous (`qraw.log.1`) and caps a run at 2 MiB by emptying the file with a note, because keeping the tail would mean rewriting the file under a lock on every cap; the message handler chains to the previous handler, or prints what Qt's would when there is none. `qraw_core` and `qraw_commands` stay without Qt and log nothing (they return diagnostics). Nothing in `src/` called `qDebug` or `qWarning` before, so there was nothing to replace; the categories are used at the points that report: file load and save, autosave and recovery, the tile pool, export, start-up.
- **Test switch.** `QRAW_DEBUG_CRASH=segv|abort|exception` (documented in BUILDING.md) rather than a hidden menu entry.
- **Limits.** Best effort: a crash that destroyed the heap or the faulting thread's stack can stop the report half way; `backtrace()` is not guaranteed async-signal-safe (it is in practice after the priming); musl has no `<execinfo.h>` (the report says so); ASan builds keep ASan's own handlers; the Windows handler is compiled in CI but no test runs it (KNOWN_ISSUES.md).

## D-050 Accessibility, keyboard navigation between cells, the Cells panel and the HIG menu rules

- **Accessible names are tested, not hoped for.** `tst_ui_accessibility` walks every visible button, combo box, line edit, spin box, slider, item view, tab and the canvas of a fully shown main window, and of every dialog `qraw --screenshot --dialog` can open (`ui::screenshotDialogNames()`; Preferences, Keyboard Shortcuts and Edit Geometry were added to that list for this), and fails on an empty `QAccessible::Name`. What Qt names itself (toolbar buttons from the action text, form rows from `QFormLayout` labels, dock title buttons) is left alone; the rest got `setAccessibleName`: search and find fields, the Layers, Cells, Welcome and Shortcuts lists, colour controls (`ColorField::setPurpose`: swatch, text, None), the zoom box, the page tabs and the "+" button. Scroll bars are named by one application filter (`ScrollBarNames`, installed by `installAccessibility()`) instead of a call per scroll area. Not walked: the line edit inside a spin box or editable combo (the control is named once), table headers.
- **The canvas is one accessible object.** `CanvasAccessible` (a `QAccessibleWidget`, role Canvas, name "Diagram", description "<page>, N shapes, M selected") is installed by `QAccessible::installFactory`, and `DescriptionChanged` is sent on selection and document changes (only while accessibility is active). Per-cell child interfaces are not built (a screen reader would need an interface object per cell, kept in step with 50 000 cells and with the tile renderer's snapshots); the Cells panel is the accessible route to the cells instead. KNOWN_ISSUES.md lists it as [NICE].
- **Tab selects cells; Ctrl+Tab leaves.** On the focused canvas Tab and Shift+Tab select the next and previous cell, Alt+Tab the first child, Alt+Shift+Tab the container. `CanvasView::focusNextPrevChild` is overridden, so Qt never moves the focus on Tab; Qt does not call it for Ctrl+Tab, and `keyPressEvent` turns that into the default focus move, which is the Qt convention for widgets that consume Tab (text editors do the same). The order is draw.io's `Graph.selectCell`: the vertices and edges that are shown, in document order (a container before its children, one layer after the other), skipping what cannot be selected (hidden, locked layer); it wraps around at the ends (in the browser draw.io's Tab clears the selection at an end and moves the focus on, `selectCell(..., noWrap)`; here leaving is Ctrl+Tab's job). Differences from draw.io: inside an entered group only that group's cells are visited (Qraw scopes selection to the entered group, draw.io's `selectCell` ignores `currentRoot`), Shift+Tab is the plain previous cell (upstream's newer `selectParentOrPreviousCell` goes to the container first; that is Alt+Shift+Tab here), and **on an empty page Tab moves the focus on** so that the keyboard is never trapped. Alt+Tab is the window switcher of most desktops and never reaches the application there; the Cells panel covers the same moves. Arrows (1 unit, Shift: grid size, one undo step per sequence) were already draw.io's and are unchanged.
- **The Cells panel** (View > Cells, dock `dock.cells`, tabbed with Layers, Outline and Find/Replace, hidden by default): a `QTreeView` over `CellTreeModel`, a read-only model of the current page built on `Page::childIds` with indices into one node table (no pointers into the page). Layers are the top rows (draw.io's empty layer name is shown as "Background"), then the cells in document order with children nested. Row text: the label as plain text (`docks::plainLabelText`, whitespace collapsed), else "<kind> (no label)"; a connector is "Connector from A to B" (+ ": label"), its ends named by label, else by kind, else "an open end". The kind is the stencil or shape name, the first style name, else Rectangle. `AccessibleDescriptionRole` carries type, absolute position and size ("Rectangle, at 40, 40, size 120 by 60"), locked and hidden. Layer rows and unselectable cells (hidden, locked layer) lack `ItemIsSelectable`. Selection syncs both ways (a guard flag, no signal loop); the current row follows the first selected cell without taking the focus; Enter (`activated`) calls `CanvasView::editLabel`, the editor the canvas uses, so there is no second mutation path. **Update rule (mirrors `DiagramScene::applyChanges`):** nothing added, removed, reordered or re-parented and no layer changed -> `dataChanged` for the changed cells and the connectors attached to them (their text names their ends); anything else, and a change of a layer (it changes which cells are selectable), rebuilds. **A hidden panel does no work:** `showEvent`/`hideEvent` activate and deactivate the model; while inactive a document change only marks it stale and the next activation rebuilds once. `tst_ui_perf_bulk` builds 50 000 cells: 20 edits while hidden cost no rebuild, the build is 24 ms (dev), label edits patch rows.
- **Icon-only buttons show their tooltip on keyboard focus** (`FocusToolTips`, one application filter per window): a button without a word on it ("+", a swatch, a tool button in icon-only style) shows its tooltip when it gets the focus by Tab, Shift+Tab or a shortcut, not by a click, and hides it on focus out. The tip is shown from a queued call because Qt's tooltip label hides itself on every focus event, including the one being handled.
- **Menus follow the KDE HIG, and a test says so** (`tst_ui_menu_conventions`, over the registry, the whole menu bar including submenus and both canvas context menus). Title Case with the small words a, an, and, as, at, but, by, for, from, in, into, of, on, or, the, to, with in lower case unless first or last (a short proper-name list for exceptions; none is needed today). **The ellipsis is the typographic "…" (U+2026), never three dots:** the HIG asks for real typographic characters, and one character is one rule for translators and tests. It ends exactly the commands that always open a dialog asking for more input: `ActionInfo::opensDialog`, set by `ActionRegistry::markOpensDialog`, which also appends it (`withEllipsis`), so the texts to translate carry none. Removed: New (opens nothing), Print Preview (shows, asks nothing), Find/Replace (shows a panel). Added to the other menus built by hand: Rename… (page tabs, user libraries), Export Library…, Choose File…, Open Existing Diagram…. "Fullscreen" is "Full Screen".
- **Shortcuts.** Function keys in use: F1 (Keyboard Shortcuts, KDE's Help key) and F2 (Edit, KDE's Rename), plus F11 for Full Screen; all are KDE standard shortcuts, none had to move, and the test fails for any other bare function key. The other bare keys are draw.io's (Delete, Backspace, Home, and X for Freehand) and the dedicated keys the platform lists next to a standard shortcut (`Key_Open`...); a new one must be added to the test on purpose. No two actions share a shortcut, none uses Meta (not on macOS, where Qt reports Control as Meta), and every `QKeySequence::StandardKey` where one exists is taken from the platform. One conflict a real Plasma session has, which the offscreen platform does not show: Plasma's theme binds Full Screen to Ctrl+Shift+F, draw.io's To Front; Full Screen keeps F11 and the platform's other bindings, and To Front keeps draw.io's key.
- **Not verified:** Orca and AT-SPI on a real desktop, VoiceOver, Narrator (KNOWN_ISSUES.md); the tests use Qt's accessibility interfaces and `QTestAccessibility`.

## D-051 Fidelity is measured against draw.io Desktop, outside the repository

- **draw.io is a reference tool, not a dependency.** `tools/fidelity/fetch_drawio.sh` downloads the official Linux AppImage of a jgraph/drawio-desktop release into a directory the caller names (it refuses the repository), checks the SHA-256 of the release's list and the SHA-512 of `latest-linux.yml`, and extracts it without FUSE. The binary and the full reference renders are never committed or redistributed (THIRD_PARTY.md); `docs/fidelity/` holds small crops of both sides as evidence of each difference class.
- **Headless without a compositor.** Electron's `--ozone-platform=headless` with `DISPLAY` and `WAYLAND_DISPLAY` unset runs the CLI export of a whole folder in one start; the sandbox flag is not needed.
- **Two scores.** Text is rasterised by two engines, so a pixel comparison never reaches zero (median 29 % of 2x2 blocks differ on files that look alike). The pixel score (2x2 blocks) says how close the pixels are; the layout score (8x8 blocks, CIE76 deltaE above 10 in both) says whether a shape, line or text block is missing, moved or drawn differently, and ranks the report. Size mismatch of the content boxes is kept apart and folded into both. The candidate is nudged by one pixel before comparing because draw.io places hairlines on half pixels.
- **Classes are counted by feature presence** (`classify.py`), and a class is only called a cause where a crop shows it and the upstream code or the Qraw log explains it.
- **The self-test is registered only with `QRAW_BUILD_TOOLS=ON`** (`tst_tools_fidelity_score`), so the default test set did not change.

## D-052 Linux packages: RPM, DEB and a Flatpak bundle, built in containers; no AppImage

- **Three formats, scripts under `packaging/`**: `common.sh`, `build-all.sh`, per-format `build.sh` (host side) and `build-in-container.sh` (repository mounted read-only, output in `dist/`), `test-install.sh`. The Flatpak needs the host's `flatpak` and `org.flatpak.Builder` (`--user`, no root).
- **No AppImage, by choice** (an earlier plan to build one on an old-glibc base with Qt downloaded from download.qt.io was dropped). The distributions' own Qt is older than 6.5 on the usual old base images, so an AppImage would need a bundled Qt and the linuxdeploy tool chain. Nothing for it is in the repository.
- **Source archive from `git archive`** (`packaging/make-source.sh`), so the RPM and DEB build exactly the committed tree; the spec and `debian/` come from the working tree.
- **Tests run in the package builds.** RPM `%check` and DEB `dh_auto_test` build with tests and run the CTest suite on the offscreen platform at `-j4` (about 20 s), with the wall-clock time budgets off as in CI (`QRAW_BENCH_TIME_BUDGETS=off`; the work-counter ceilings still apply). No test is excluded (earlier four were: causes found and fixed, CHANGELOG.md, "CI repair"). `rpmbuild --without check` and `DEB_BUILD_OPTIONS=nocheck` skip it. A DejaVu font is a build requirement (the offscreen platform has no other font in a container).
- **The RPM is built with Fedora's default LTO.** The Qt big resources (the vendored style sheet, stencils and icons, compiled into static libraries) are patched by rcc in a second pass and came out empty under `-flto`, which an earlier version of the spec worked around by switching LTO off; `qraw_add_big_resources` compiles the one object that rcc patches without LTO instead.
- **Build parallelism is capped at 6** (`JOBS`, `_smp_ncpus_max`, `parallel=`, `--jobs`): each C++ compile process takes about 0.5 GB.
- **DEB targets.** Built in `debian:trixie` (Qt 6.8); the shlibs dependencies make it installable on Debian 13 and Ubuntu 25.10, 26.04 and 26.10 and uninstallable on Ubuntu 24.04 (Qt 6.4 < 6.5), which the install test checks.
- **Flatpak bundle** records the Flathub runtime repository, so installing it pulls the KDE 6.11 runtime. Install tests use `--user` and remove the app afterwards.
- **CI:** job `linux-packages` in `ci.yml` builds all three and uploads artifacts only; no release, nothing published.

## D-053 The diagram follows the application theme by default

- **Problem.** View > Dark Diagram (D-043) was independent of the theme, so a dark UI showed a white canvas. draw.io has one appearance setting (light, dark, or automatic with `prefers-color-scheme`) that drives the UI and the canvas together (`Editor.darkMode`, `EditorUi.setDarkMode`), so a dark draw.io is dark all the way through.
- **Decision.** `AppSettings::diagramAppearance` is `FollowTheme` (default), `Light` or `Dark`. `resolveDiagramDark(theme, appearance, osScheme)` (`ui/diagram_scheme.h`, a pure function) gives the scheme: an explicit appearance wins; otherwise Light is light, Dark and High Contrast are dark (the High Contrast palette is white on black), and System takes the OS scheme (`QStyleHints::colorScheme`, Unknown counts as light). The main window resolves it at start, when Preferences are applied, when the View > Diagram Appearance actions change it and on `QStyleHints::colorSchemeChanged`, and hands the result to `DocumentSession::setDiagramDark`, the one existing path that rebuilds the view and rasterises the tiles again.
- **Why the override stays.** A dark UI around a light canvas is a normal wish (the diagram is going to be exported or pasted on white). It is an exclusive submenu rather than a checkbox because three states exist; the old boolean migrates on read (true is Dark, false is Follow Theme), and writing the new value removes the old key.
- **Around the page.** The tile decoration already had dark colours for the backdrop, the grid and the page border; the outline view's fill and the overlay follow the scheme too. Handles, selection, guides and the rubber band keep draw.io's colours (blue, legible on both pages; a test checks the contrast), the drop target follows `EditorUi.setDarkMode` (`#00ff00` dark, `#0000ff` light). There is no page shadow in Qraw.
- **System theme and the palette.** `applyTheme(System)` used to set a copy of the startup palette, which pins the palette; it now resets to the default palette so the platform keeps it in step with the OS scheme, as it keeps the canvas.
- **Exports** keep their own explicit choice (the dialog's checkbox, `--dark`); only its default comes from what the canvas shows.
- **Tests.** The offscreen platform cannot change `QStyleHints::colorScheme`, so the live OS change is tested by emitting `colorSchemeChanged`.
